## 사용자 피드백 (원문)

### 주문 테이블 피드백
- 고객(회원, 비회원) 주문 날짜 및 시간이 없음
- 결제용 주문번호의 형태는 회원과 비회원이 같은지
- 주문 상태에 돈의 상태라고 했는데 이 부분 설명해줘
- 상태변경일시, 상태변경주체, 상태변경메모는 무슨역할을 하는지, 혹시 주문이력테이블에 들어가야하는건지 아니면 상품상태이력으로 따로 테이블을 만들어서 컬럼추가해야할지
- 배송 진행 요약이 주문 테이블에 있는 이유는?
- 정가 합계에 대한 설명 필요, 그냥 only 금액인지, 쿠폰+금액, 포인트+금액을 정가 합계라고 하는지
- 정가합계, 상품 할인 합계, 판매가 합계는 결제에 들어가도 되지 않아? 왜 주문 테이블에 있는건지
- 쿠폰 할인액도 결제나 쿠폰 테이블에 있어야하는거아닌지, 주문 테이블에 있는 이유
- 기본 배송비, 추가 배송비, 배송비 합계, 배송비할인액 이건 아직 안 만든 배송테이블에 있어야하는거아니야? 주문테이블에 있는 이유 좀
- 최종 결제액은 결제에 있어도 되는거 아니야? 결제ID를 FK로 가져오면 되는거 아닌가?
- 주문자 전화 검색값의 역할은?
- 결제 완료 일시도 결제 테이블에 있어야 하는거 아니야? 아니면 결제ID를 FK로 가져와서 결제관련된 것들을 참조하면 되잖아.
- 개인정보 파기 일시는 고객테이블에 있어야하지 않아? 이거 비회원이 주문하면 주문완료 후에 파기한다고 하는거야?
- 주문 테이블에 왜 재고관련된 항목들은 없어? 재고ID를 FK로 참조를 하던 해야하지 않아? 주문이랑 재고는 꽤 밀접한 관련이 있을 것 같은데

### 주문 상품 테이블 피드백
- 줄 번호라는 컬럼의 역할이랑 왜 주문 상품 테이블에 있는지
- 할인액이랑 할인 행사명은 할인 행사 ID에 속하는거 아니야?
- 정가 소계는 왜 주문 상품 테이블에 있는거야? 정가로 판매하는거 아니잖아
- 할인 소계랑 판매가 소계도 왜 이 테이블에 있는지 설명 좀
- 쿠폰 배분액 설명에 이 줄이 나눠 가진 쿠폰 할인이라고 했는데 쿠폰은 상품당 1개 씩만 사용가능하게 했는데 나눠가진다는건 무슨 말이지?
- 실결제액은 굳이 따지자면 주문테이블에 있어야하지 않아? 주문 상품 테이블에 있는 이유는
- 상품 상태 컬럼 설명을 보면 결제, 배송, 상품에도 연관있는데 그럼 그쪽 테이블에도 있는거야? 상품 테이블에 있어야 할 것 같은데
- 여기서도 상태 변경 일시, 상태 변경 주체, 상태 변경 메모가 있는데 상품 테이블에 있거나 별도로 상품이력테이블 만들어서 거기에 둬야하지 않아? 왜 주문 상품 테이블에 있는거야?
- 결제 완료 일시도 결제ID FK로 참조 받을 수 있지 않아? 만약에 1번의 결제로 2가지 이상 상품을 주문했을 경우도 생각해봤어?
- 상품 준비 일시 컬럼은 어떤 역할이야? 재고나 상품 쪽 테이블에 있어야하지 않나?
- 출고일시는 재고 쪽이나 배송 쪽에 관련 있을 것 같은데
- 생성일시는 뭘 의미하는 컬럼이야? 상품이 생성된 일시를 말하는거야? 그렇다면 상품 쪽 테이블로 가야할 것 같은데

### 배송지, 배송지 변경 이력
- 배송 테이블 만들고 볼게

### 주문 상태 이력 테이블 피드백
- 주문 상태 이력 컬럼이 정말 이게 다야? 너무 적은거 아니야? 누가 변경했는지 변경자도 없는데
- 어느 부분이 변경되었는지 변경된 부분 같은 컬럼 있어야 되지 않아? 배송지가 변경되었는지 상품이 변경이 되었는지 받는 사람이 변경되었는지

### 주문 상품 상태 이력 테이블 피드백
- 여기도 변경자가 없어. 고객이 직접 변경했는지 예를들면 고객이 원하는 상품의 컬러가 없어서 고객에게 말하고 고객이 원하는 컬러를 직원이 변경했는지
- 그리고 여기도 변경된 부분에 대한 것이 없어, 컬러가 변경되었는지, 사이즈가 변경되었는지 등

### 배송비 규칙, 추가 배송비 지역, 택배사
- 배송 도메인 테이블 만들고 확인할게

### 출고 상품 테이블 피드백
- 출고 상품도 상품 테이블이랑 재고 테이블이랑 연관있지 않아? 출고 되었으면 재고 수량 마이너스 카운트 해야하잖아.
- 컬럼에 우리가 얘기했던 재고 마이너스 카운트 하는 시점 결제인지 출고인지 출고로 했으면 그 시점도 컬럼으로 있어야 할 것 같고, 출고된 시간으로 하던
- 출고된 상품 어느 택배사에 가져갔는지도 중요하지 않아?
- 그리고 출고 되었으면 운송장번호도 있어야 하고
- 그리고 아직 배송 테이블 하지 않았지만 출고해서 다이렉트로 고객한테 가는거 아니면 중간에 집하하고 다시 고객한테 간다거나 하는 부분도 신경써야하고

### 고객(회원·비회원)
- 회원 비회원은 고객 테이블로 들어가는게 맞는거 같아.
- 회원도 쇼핑몰 사이트에서 회원가입한 회원이 있고 깃허브나 구글, 네이버, 카톡에 연동해서 로그인하는 회원도 있잖아. 그렇게 세부적으로 나누면 좋을 것 같아
- 지금 현재 테스트 사이트는 깃허브로 로그인 하는데 깃허브에서 회원의 어떤 정보를 가지고 로그인 시켜주는거야?

### 비회원 출입증 테이블 피드백
- 컬럼에 출입증ID가 있는데 이건 1회용이야? 비회원이 주문 하고 상품받으면 자동으로 삭제되거나 사용못함으로 바껴? 그거 확인해봤어?
- 출입증ID는 그럼 같은 비회원인 사람이 다시 주문하려고 하면 재발급 받는거야?
- 토큰 해시는 여기 테이블에서 무슨 역할 해?
- 무효처리 일시는 뭔지 설명해봐

### 비회원 조회 시도 기록
- 왜 만든거야? 만든 이유 설명 좀

### 전체
- 전체적으로 컬럼수가 너무 적어. 너무 부족해. 설명도 부족해. 표를 보면 설명이 빈칸인 컬럼이 너무 많아.
- 설명에 이유를 적거나 칸이 너무 작으면 테이블 당 컬럼 하나씩 해서 사용한 이유도 같이 있었으면 좋겠어. 그럼 더 자세하게 피드백하거나 그 컬럼이 테이블에 있는걸 납득할거 같아.
  → **앞으로 테이블 정의를 보여 줄 때는 논리명·물리명과 함께 모든 컬럼에 "왜 이 테이블에 있나(이유)"를 빈칸 없이 적는다.**

## Claude 답변

### 0. 큰 그림: 왜 금액·상태가 "주문"에 있는가

| 테이블 | 비유 | 담는 것 |
|---|---|---|
| Order (주문) | 계약서·청구서 | 무엇을, 얼마에, 어디로 보내기로 약속했나. 주문 순간에 정해지고 바뀌지 않음 |
| Payment (결제) | 영수증·입금 기록 | 그 청구서에 대해 돈이 실제로 들어왔나. 시도할 때마다 1줄 |
| Sku/Style (상품) | 카탈로그 | 지금 파는 상품 정보. 수천 개 주문이 같은 상품을 함께 가리킴 |
| Shipment (출고) | 택배 상자 | 실제로 보낸 상자 1개 = 송장 1개 |

주문 1건에 결제가 여러 줄 생길 수 있음:
```
주문 20261118-48213907 (청구 130,000원)
 ├ 결제 시도 1: 카드 → 한도 초과로 실패 (ABORTED)
 ├ 결제 시도 2: 가상계좌 발급 → 입금 안 해서 만료 (EXPIRED)
 └ 결제 시도 3: 퀵계좌이체 → 성공 (DONE) → 나중에 티셔츠만 반품해서 부분 취소
```
- FK는 Payment.orderId → Order 방향(N:1). Order에 paymentId를 두면 어느 시도를 가리켜야 할지 정할 수 없음.
- 결제 금액은 부분 취소 때마다 줄어들지만(balanceAmount), "원래 얼마짜리 주문이었나"는 변하면 안 되므로 둘을 따로 둠.
- 트리거가 `Payment.amount = Order.totalPrice`가 아니면 결제 줄을 만들지 못하게 막음. 실무에서도 주문서 금액과 PG 승인 금액을 따로 저장하고 매일 대조(대사)함.

### 1. 주문 Order: 컬럼별 이유

| 논리명 | 물리명 | 왜 이 테이블에 있나 |
|---|---|---|
| 주문 ID | id | 내부 연결용 번호. 순번이라 노출하면 하루 주문 수가 드러나므로 화면에는 안 씀 |
| 주문번호 | orderNo | 고객용 번호. 회원·비회원 모두 `한국날짜-무작위8자리`. 비회원 조회 열쇠 |
| 결제용 주문번호 | paymentOrderId | 토스에 보내는 번호. **회원·비회원 모두 `order_` + UUID로 같은 형식**(checkout.ts:249, 364). 따로 두는 이유: 토스 형식 규칙, PG사를 바꿔도 고객 주문번호 유지, 결제 URL에 고객 번호 미노출 |
| 주문명 | orderName | 토스 결제창 표시값. 결제 시도마다 같아야 해서 주문에 고정 |
| 고객 ID | customerId | User가 아니라 Customer → 탈퇴해 User가 지워져도 주문이 남음 |
| 주문자 구분 | ordererType | 비회원으로 산 사실을 가입 후에도 보존. 비회원 쿠폰·포인트 0원 CHECK의 근거 |
| 회원 연결 일시 | linkedAt | 비회원 주문을 회원 계정으로 가져온 시각 |
| 주문 경로 | channel | PC/모바일 통계 |
| 주문 상태 | status | 돈의 상태(아래) |
| 상태 변경 일시·주체·메모 | statusChangedAt/By/Memo | 마지막 변경의 언제·누가·왜. 트리거가 이 값으로 OrderStatusHistory에 자동 기록(아래) |
| 배송 진행 요약 | fulfillmentStatus | 목록·검색용 요약(아래) |
| 정가 합계 | itemsListTotal | 상품 정가 × 수량의 합만. 쿠폰·포인트·배송비 미포함 |
| 상품 할인 합계 | itemsDiscountTotal | 할인 행사로 깎인 금액 합 |
| 판매가 합계 | itemsTotal | 정가 합계 − 상품 할인. 무료배송 기준 판단 금액이라 주문 시점 고정 |
| 쿠폰 할인액 | couponDiscountTotal | 어떤 쿠폰인지는 OrderCoupon. 여기는 청구서 계산식의 합계 한 줄 → DB CHECK가 계산식을 한 행에서 검사 |
| 기본·추가 배송비, 배송비 합계, 배송비 할인 | shippingBaseFee 등 | 고객에게 청구하는 배송비는 결제 전 주문서에서 정해지는 계약 금액. 출고(상자)는 결제 뒤에 생기고 상자 2개로 나눠도 배송비는 한 번. 배송 도메인에 들어갈 택배 운임(원가)과는 다른 숫자 |
| 포인트 사용액 | pointUsed | ⑭ 자리. 계산식 CHECK에 포함 |
| 최종 결제액 | totalPrice | 청구서 총액. 결제는 이 금액을 복사하고 트리거가 일치 검사 |
| 배송비 규칙 ID | shippingPolicyId | 당시 배송비의 근거 |
| 무료배송 기준액 | freeShippingThreshold | 반품 시 왕복 배송비 판단의 근거(당시 기준) |
| 주문자 이름·전화·이메일(암호화) | ordererNameEnc 등 | 주문 당시 주문자 사본. 회원 정보가 바뀌거나 탈퇴해도 유지(법정 보관) |
| 주문자 전화 검색값 | ordererPhoneHash | 암호문은 같은 번호라도 매번 달라 검색이 안 됨 → HMAC 값으로 고객센터 "전화번호로 주문 찾기". 원래 번호로 되돌릴 수 없음 |
| 결제 완료 일시 | paidAt | 주문이 PAID가 된 시각(가상계좌는 입금 시각). 결제가 여러 줄이라 매출 집계 편의용 중복. 제거 가능(⑤) |
| 취소 일시 | canceledAt | 취소·만료 시각 |
| 구매확정 일시 | confirmedAt | 모든 상품 확정 시각 |
| 개인정보 파기 일시 | piiPurgedAt | 주문 안 개인정보 사본 파기 시각(아래) |
| 반품 완료 일시 | returnedAt | 마지막 반품 완료 |
| **주문 일시** | createdAt | **주문 날짜·시간은 이 칸.** 논리명을 "생성 일시"로 적어 없는 것처럼 보였음 → "주문 일시"로 정정(⑥) |
| 수정 일시 | updatedAt | 마지막 수정 시각 |

금액 예시(정가 합계는 상품 금액만):
```
자켓  정가 100,000 × 1개, 할인 20%  → 판매가  80,000
티    정가  30,000 × 2개, 할인 없음 → 판매가  60,000
정가 합계 160,000 / 상품 할인 −20,000 / 판매가 합계 140,000 (5만 원 이상 → 기본 배송비 무료)
쿠폰 −10,000 / 배송비 0 / 포인트 0 → 최종 결제액 130,000 (= Payment.amount)
```

- **돈의 상태**: Order.status는 결제 대기 → 입금 대기 → 결제 완료 → 취소/만료/취소 실패, 돈의 진행만 나타냄. 물건 진행은 주문 상품마다 따로 둠. 한 주문 안에 "자켓 배송중 / 티 취소 / 바지 반품 요청"이 동시에 있을 수 있어서 한 칸으로는 표현할 수 없음.
- **상태 변경 3종**: 이력 테이블은 이미 따로 있음(OrderStatusHistory, OrderItemStatusHistory). 상태를 바꿀 때 3칸을 함께 바꾸게 강제하고, 트리거가 그 값으로 이력을 자동 기록함 → 이력이 빠질 수 없음. **부족한 점**: By가 역할(CUSTOMER/ADMIN/SYSTEM)만 남기고 누구인지는 없음 → 개선안 ①.
- **배송 진행 요약**: "출고 대기 주문 목록" 같은 목록·검색 때 모든 상품 상태를 매번 계산하지 않으려는 요약 칸. 트리거만 계산하고 앱은 못 씀.
- **개인정보 파기**: Customer에는 탈퇴 익명화용 anonymizedAt이 따로 있음. 주문 안 주문자·배송지는 별도 사본이고 전자상거래법상 계약·대금결제·청약철회 기록은 5년(분쟁 기록은 3년) 보관 → 주문 5년 뒤 파기. **비회원도 주문 완료 직후가 아니라 5년 뒤** 파기(비밀번호 해시도 함께).
- **재고**: 연결은 주문 상품 줄 단위로 있음. `Order ─< OrderItem ─< InventoryReservation(orderId, orderItemId, skuId, 창고, 수량, 예약 → 할당(결제) → 확정(출고, 실재고 −), shipmentId) ─> InventoryBalance`. 주문 1건에 SKU가 여러 개라 주문에 재고 FK 하나를 둘 수 없음. 예약은 다시 잡히면 여러 줄이 생겨서 예약 → 주문 상품 방향(N:1).

### 2. 주문 상품 OrderItem: 컬럼별 이유

| 논리명 | 물리명 | 왜 이 테이블에 있나 |
|---|---|---|
| 줄 번호 | lineNo | 주문 안의 1, 2, 3번. id는 전체 번호라 고객에게 의미 없음. "2번 상품만 취소", 표시 순서, 부분 취소·반품 지목용 |
| SKU ID / 수량 | skuId / quantity | 산 컬러 × 사이즈와 수량 |
| 정가 / 할인액 / 판매가 | listPrice / discountAmount / price | 주문 당시 가격 사본. 행사는 할인율 변경·종료·삭제(promotionId SetNull)될 수 있고, 최대 할인·절사·대상별 할인율 때문에 상품마다 할인액이 달라서 행사 ID로는 되살릴 수 없음. 할인 표시의 법적 근거 |
| 할인 행사 ID / 행사명 | promotionId / promotionName | 행사 연결(통계) / 이름이 바뀌거나 행사가 삭제돼도 남는 사본 |
| 정가·할인·판매가 소계 | lineListTotal / lineDiscountTotal / lineTotal | 정가로 판다는 뜻이 아니라 할인 전 → 후 표시와 통계용. `단가 × 수량`으로 계산할 수 있는 편의용 중복(CHECK로 일치 보장). 제거 가능(⑤) |
| 쿠폰 배분액 | couponAllocated | 아래 |
| 포인트 배분액 | pointAllocated | 포인트도 같은 방식으로 배분(⑭) |
| 실결제액 | payAmount | 주문 전체 결제액은 Order.totalPrice에 따로 있음. 이 칸은 줄별 실제 낸 돈으로 부분 취소·반품 환불의 기준 |
| 상품 정보 사본 | styleCode 등 | 상품명·이미지가 바뀌거나 판매가 종료돼도 산 당시 그대로 |
| 상품 상태 | status | 아래 |
| 상태 변경 3종 | statusChanged* | 주문과 같음. 트리거가 OrderItemStatusHistory에 기록 |
| 결제 완료 일시 | paidAt | 결제는 주문 단위 1번 → 트리거가 모든 줄을 한꺼번에 PAID로 바꿈. 지금은 Order.paidAt과 같은 중복(⑤) |
| 상품 준비 일시 | preparingAt | 이 주문 이 상품의 포장 시작 시각. 이때부터 고객 취소·배송지 변경 불가, 결제 → 준비 소요 시간 통계. 상품·재고의 속성이 아님 |
| 출고 일시 | shippedAt | 원본은 Shipment.shippedAt(상자)과 InventoryLedger.occurredAt. 트리거가 복사. 줄마다 다른 상자로 나갈 수 있어서 줄마다 둠 |
| 배송 완료·구매확정·취소·반품 완료 일시 | deliveredAt 등 | 상태별 진입 시각(CHECK) |
| 구매확정 방식 | confirmType | 수동 / 7일 뒤 자동 |
| 자동 구매확정 예정 일시 | autoConfirmAt | 배송 완료 + 7일, 자동 확정 작업이 대상을 찾는 칸 |
| **주문 상품 등록 일시** | createdAt | 상품 생성 시각이 아니라 이 주문 줄이 만들어진 시각(= 주문 시각). 상품 생성은 Style.createdAt → 논리명 정정(⑥) |

- **쿠폰 배분**: 규칙은 상품당 1장이 아니라 **주문당 1장**. 종류: 상품 쿠폰(1줄이 전부 가짐), **장바구니 쿠폰(조건 맞는 여러 줄 합계에서 할인 → 금액 비율로 나눔)**, 배송비 쿠폰(줄에는 0). 예: 자켓 80,000 + 티 60,000에 10,000원 쿠폰 → 자켓 5,714 / 티 4,286. 티만 반품하면 환불은 60,000 − 4,286 = 55,714원.
- **상품 상태가 상품 테이블이 아닌 이유**: SKU는 카탈로그라 수천 주문이 공유함. "배송중"은 이 고객이 산 이 줄의 상태. 상품에는 다른 의미의 상태(판매중 등 Style.status)가 있음. 결제(돈)·출고(상자)는 각자 상태가 있고, 트리거로 연결됨(결제 완료 → 줄들 PAID, 상자 출고 → 그 상자의 줄들 SHIPPED + 재고 확정 차감).

### 3. 주문 상태 이력 / 주문 상품 상태 이력
지적이 맞음. 지금은 상태 칸 변화만 기록함.
- 변경자: 역할만 있고 누구인지 없음.
- 무엇이 바뀌었나: 상태만. 배송지는 OrderShippingAddressHistory에 따로 있지만 받는 사람이 바뀐 건지 주소가 바뀐 건지 한눈에 안 보임.
- 옵션(컬러·사이즈) 변경: **기능 자체가 없음**. 실무에서는 새 SKU 재고 예약과 옛 예약 해제, 가격 차액(보통 같은 가격 옵션만), 상품 정보 사본 교체, 변경 전후 기록이 함께 필요함 → 개선안 ②.

### 4. 출고 상품 ShipmentItem
- 출고 시 재고 차감은 **구현돼 있음**: Shipment SHIPPED → 트리거가 재고 예약을 CONFIRMED로 → 재고 원장에 SALE −수량 → 실재고 감소(결제가 아니라 출고 시점).
- 차감 시점: Shipment.shippedAt = InventoryReservation.confirmedAt = InventoryLedger.occurredAt.
- 택배사·운송장 번호: Shipment.courierId / trackingNo. 송장은 상자 단위라 상자에 둠(상품마다 두면 반복되고 어긋날 수 있음). ShipmentItem은 "상자에 어느 주문 상품 줄이 몇 개 들었나"를 잇는 연결표.
- 집하·허브 경유 단계는 없음(상자 상태가 준비·출고·완료뿐) → 배송 도메인에서 배송 추적 이벤트 테이블로 설계(⑦).

### 5. 고객 유형·로그인 방식, GitHub 로그인 정보
- 지금 Customer는 회원만 있고, 비회원은 주문 안의 주문자 사본으로만 존재함. 로그인 방식은 User(사람) ─< Account(provider = github/google/naver/kakao)로 이미 여러 개를 둘 수 있는 구조이고, 지금은 GitHub만 켜 둠. 자체 가입(아이디·비밀번호) 테이블은 없음.
- 비회원을 고객 테이블에 넣을 때 쟁점: 본인 확인이 없어서 같은 전화번호를 같은 사람으로 보장할 수 없음 → 개선안 ③.
- GitHub 로그인 흐름: 동의 → 일회용 코드 → 서버가 비밀키로 접근 토큰 교환 → GitHub API로 프로필 조회(scope `read:user, user:email`, DB 확인). 저장 정보: GitHub 사용자 번호(Account.providerAccountId, 진짜 신원 열쇠), 이름(User.name), 대표 이메일(User.email), 프로필 사진(User.image), 접근 토큰·scope(Account). 비밀번호·전화·주소·생년월일은 받지 않음.
- **발견한 문제**: GitHub 접근 토큰이 Account.access_token에 **평문으로 저장**돼 있음(1행 확인, 값 미출력). 로그인 뒤 쓰지 않는 값이라 유출 위험만 있음. 원인은 Auth.js Prisma 어댑터의 기본 동작 → 개선안 ④.

### 6. 비회원 출입증 GuestOrderSession
- 한 번 쓰면 사라지는 방식이 아니라 **시간 제한형**: 주문 출입증 60분, 조회 출입증 30분.
- 배송 완료와는 무관함. 시간이 지나면 저절로 무효, 회원이 가져가면 즉시 무효(revokeGuestSessions). 지난 출입증은 `orders:jobs -- guest-cleanup`이 삭제함. 확인 당시 DB에 2개가 남아 있었고 둘 다 만료·무효였음(정리 작업 미실행, 배포 후 cron 예정).
- 같은 사람이 다시 주문하면 새 주문에 새 출입증. 비회원은 사람이 아니라 주문에 묶임. 지난 주문은 주문번호 + 비밀번호 조회로 새 출입증을 받음.
- 토큰 해시: 쿠키에는 무작위 토큰, DB에는 SHA-256 해시만 저장. DB가 유출돼도 쿠키를 만들 수 없음.
- 무효 처리 일시: 만료 전에 강제로 끈 시각(지금은 회원 가져오기 때).

### 7. 비회원 조회 시도 기록 GuestLookupAttempt
- 비회원 열쇠가 주문번호 + 비밀번호뿐이라 무작위 대입 공격에 노출됨 → ① 같은 IP에서 1시간 20회 실패 시 차단하려면 시도 기록이 필요(주문별 5회 잠금은 GuestOrderAccess가 담당) ② 조회 감사·사고 추적 ③ IP 원문 없이 HMAC + 가린 IP만, 90일 뒤 삭제.
