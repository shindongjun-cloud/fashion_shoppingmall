# 재설계 1/5: 고객 도메인 (B안: 공통 + 역할별 분리)

> 2026-11-23 작성. 기존 설계(테이블 82개, `prisma/schema.prisma`)는 그대로 두고 처음부터 다시 설계하는 문서입니다.
> 순서: **고객 → 상품 → 주문 → 결제 → 배송**. 벤치마크: lookple.com(남성 쇼핑몰, 카페24).
> 아직 스키마·코드에는 반영하지 않았습니다(사용자 검토 → 확정 → 반영).

## 1. 확정 요구사항 (사용자와 대화로 정함)

| 항목 | 결정 |
|---|---|
| 회원 유형 | 개인 / 사업자(개인사업자·법인사업자·기관단체) / 외국인(국내 거주, 한국 휴대폰 인증) |
| 비회원 | 주문마다 비회원 고객 1행(합치지 않음). 가입 후 주문번호+비밀번호 또는 본인인증으로 회원에게 옮김 |
| 로그인 | 자체 아이디·비밀번호 + 소셜(카카오·네이버·구글·애플, 깃허브는 개발용). 한 회원에 여러 개 연결, 마지막 수단은 해제 불가 |
| 본인인증 | 가입 필수(테스트는 가짜 인증). CI 해시로 1인 1계정, 14세 미만 가입 차단. 주민번호·외국인등록번호는 저장하지 않음 |
| 사업자 확인 | 국세청 진위확인 자동(테스트는 가짜), 결과·시각 저장, 폐업이면 가입 불가 |
| 수집 범위 | 필수: 이름·휴대폰·이메일 / 선택: 성별·생일·체형. 룩플식 추가정보(학력·소득·자동차 등)는 받지 않음(최소 수집) |
| 동의 | 약관 버전별 필수·선택 동의와 철회 이력. 마케팅 SMS·이메일·앱 푸시. 광고 수신 동의 2년마다 재확인 통지 |
| 등급 | 등급 기준 + 등급 변경 이력 |
| 휴면 | 1년 미접속이면 휴면(본인인증 후 해제, 마케팅 중단). 평생회원을 고르면 휴면 제외 |
| 탈퇴 | 신청 → 7일 유예(철회 가능) → 개인정보 파기. 같은 사람은 30일 재가입 제한 |
| 주소록 | 여러 개(최대 10개) + 기본 배송지 1개 |

법 관련 메모
- 2023년 9월 개인정보보호법 개정으로 "1년 미이용 시 파기·분리 보관" 의무(유효기간제)가 없어졌습니다. 휴면은 법적 의무가 아니라 **쇼핑몰 정책**입니다. 룩플의 "평생회원"은 예전 의무를 피하려고 생긴 기능인데, 정책으로 그대로 따릅니다.
- 광고성 정보 수신 동의를 받은 사람에게는 **2년마다** 동의 유지 사실을 알려야 합니다(정보통신망법 시행령). 야간(21시~다음날 8시) 광고 푸시는 별도 동의가 필요합니다.
- 개인정보 **처리 위탁**(택배사·PG사 등)은 동의 대상이 아니라 처리방침에 공개하면 됩니다. 룩플의 "처리 위탁 동의(선택)" 체크박스는 두지 않습니다.

## 2. 테이블 관계도

```
CustomerGrade(등급 기준) ──< Customer(고객 공통) >── Customer(비회원 행 → 합쳐진 회원 행, mergedIntoCustomerId)
                               │
     ┌─────────────┬──────────┼───────────┬──────────────┬──────────────┐
     1:1           1:1        1:N          1:N            1:1            1:1
CustomerProfile  CustomerCredential  CustomerSocialAccount  CustomerVerification  CustomerBusiness  CustomerForeigner
(개인정보)        (자체 아이디)        (소셜 연결)             (본인인증 기록)         (사업자 상세)       (외국인 상세)

     ├─ 1:1 CustomerBodyProfile (체형)          ├─ 1:N CustomerAddress (주소록)
     ├─ 1:N CustomerConsent (동의 이력) >── TermsVersion (약관 버전)
     ├─ 1:N CustomerMarketingPreference (채널별 수신 상태)
     ├─ 1:N CustomerGradeHistory (등급 이력)    ├─ 1:N CustomerStatusHistory (상태 이력)
     ├─ 1:N CustomerWithdrawal (탈퇴 신청)      └─ 1:N CustomerLoginHistory (로그인 기록)
```

**행이 있으면 그 역할이 있다**는 원칙입니다. 예를 들어 사업자 회원만 `CustomerBusiness` 행이 있고, 비회원은 `CustomerProfile` 행만 있고 로그인·인증·등급 행이 없습니다.

| 고객 종류 | Customer | Profile | Verification | Credential / Social | Business | Foreigner | 등급 |
|---|---|---|---|---|---|---|---|
| 개인회원 | ○ | ○ | ○ | 1개 이상 | ✕ | ✕ | ○ |
| 사업자회원 | ○ | ○(담당자) | ○ | 1개 이상 | ○ | ✕ | ○ |
| 외국인회원 | ○ | ○ | ○(외국인) | 1개 이상 | ✕ | ○ | ○ |
| 비회원 | ○ | ○(주문자) | ✕ | ✕ | ✕ | ✕ | ✕ |

## 4. 테이블 정의

### 4-1. 고객 `Customer`
회원과 비회원 모두가 한 줄씩 갖는 **공통 테이블**입니다. 주문·쿠폰·포인트 등 다른 도메인은 모두 이 테이블의 `id`를 가리킵니다. 그래서 회원이 탈퇴해 로그인 수단이 사라져도 주문 기록이 남습니다. 개인정보는 여기에 두지 않고 `CustomerProfile`로 분리합니다. 이렇게 하면 고객 목록·통계를 볼 때 암호문을 건드리지 않습니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 고객 ID | id | [PK] 정수, 자동 증가. 다른 테이블이 연결할 때만 쓰는 내부 번호입니다. 순번이라 노출하면 가입자 수가 드러나서 화면·URL에는 쓰지 않습니다. |
| 고객번호 | customerNo | [UK] 필수. `C` + 무작위 숫자 10자리. 고객센터·관리자 화면에 보이는 번호입니다. 순번이 아니라서 다른 고객 번호를 추측할 수 없습니다. |
| 고객 구분 | customerKind | 필수. `MEMBER`(회원) / `GUEST`(비회원). 비회원도 고객 테이블에 넣기로 해서, 둘을 가르는 칸이 필요합니다. 한 번 정하면 바뀌지 않습니다. 비회원이 가입하면 이 행이 회원으로 바뀌는 게 아니라 새 회원 행이 생기고, 이 행은 합쳐짐(MERGED) 처리됩니다. |
| 회원 유형 | memberType | 회원만 필수, 비회원은 비움. `PERSONAL`(개인) / `BUSINESS`(사업자·기관·단체) / `FOREIGNER`(외국인). 어느 상세 테이블(Business·Foreigner)에 행이 있어야 하는지 정하는 기준이라 공통 테이블에 둡니다. 가입 후 바꿀 수 없습니다(바꾸려면 탈퇴 후 재가입, 룩플과 같음). |
| 고객 상태 | status | 필수. 회원: `ACTIVE`(정상) / `DORMANT`(휴면) / `SUSPENDED`(이용 정지) / `WITHDRAW_PENDING`(탈퇴 유예 중) / `WITHDRAWN`(탈퇴 완료). 비회원: `ACTIVE` / `MERGED`(회원 계정으로 합쳐짐). 로그인·주문 가능 여부를 이 칸 하나로 판단합니다. |
| 상태 변경 사유 코드 | statusReasonCode | 필수. 예: `SIGNUP`(가입), `INACTIVE_1Y`(1년 미접속), `LOGIN_REACTIVATED`(로그인해서 휴면 해제), `ABUSE`(부정 이용), `CUSTOMER_REQUEST`(본인 요청), `GUEST_CLAIMED`(비회원 주문 가져가기). 상태를 바꿀 때 함께 바꾸면 트리거가 상태 이력에 복사합니다. 이력이 빠지지 않게 하는 장치입니다. |
| 상태 변경 주체 | statusChangedByType | 필수. `CUSTOMER` / `ADMIN` / `SYSTEM`. 지난 피드백("누가 바꿨는지 없다")을 반영해, 역할과 아래 처리자 ID를 함께 남깁니다. |
| 상태 변경 처리자 | statusChangedById | 선택. 주체가 ADMIN이면 필수로, 관리자 ID를 적습니다(관리자 테이블은 관리자 도메인에서 FK로 연결, 그전에는 문자열). CUSTOMER면 본인이라 비우고, SYSTEM이면 작업 이름(예: `job:dormant`)을 적습니다. |
| 상태 변경 메모 | statusMemo | 선택. 사유 코드로 부족할 때 덧붙이는 설명(예: 정지 사유 상세). |
| 상태 변경 일시 | statusChangedAt | 필수. 마지막으로 상태를 바꾼 시각. 바꿀 때마다 새 값이어야 합니다(트리거 검사). |
| 등급 ID | gradeId | [FK→CustomerGrade] 회원만 필수, 비회원은 비움. 현재 등급입니다. 쿠폰·적립률·무료배송 판단 때마다 이력을 뒤지지 않도록 현재 값을 여기에 둡니다. 바꾸려면 등급 이력을 먼저 넣어야 합니다(트리거). |
| 평생회원 여부 | isLifetimeMember | 필수, 기본 false. 회원이 "평생회원"을 고르면 true. 1년 미접속이어도 휴면으로 바꾸지 않습니다. 비회원은 항상 false입니다. |
| 평생회원 선택 일시 | lifetimeChosenAt | 평생회원이면 필수. 룩플처럼 "평생회원 쿠폰을 받으면 3개월 유지"를 적용할 때 기준이 되는 시각입니다. |
| 가입 경로 | joinChannel | 회원만 필수. `WEB` / `MOBILE_WEB` / `APP` / `ADMIN`(직원이 대신 등록). 경로별 가입 통계용입니다. |
| 가입 일시 | joinedAt | 회원만 필수. 회원가입을 완료한 시각. 비회원 행은 비웁니다(`createdAt`이 첫 주문 시각). |
| 마지막 로그인 일시 | lastLoginAt | 선택. 휴면 대상을 찾는 기준입니다. 로그인할 때마다 갱신합니다(자세한 기록은 로그인 기록 테이블). |
| 마지막 주문 일시 | lastOrderAt | 선택. 마지막으로 결제를 완료한 시각. 등급 산정·재구매 분석에 쓰며, 매번 주문 테이블을 뒤지지 않으려고 둡니다. |
| 휴면 예정 안내 일시 | dormantNoticeSentAt | 선택. 휴면 전환 30일 전 안내를 보낸 시각. 같은 안내를 두 번 보내지 않도록 기록합니다. 법적 의무는 없어졌지만 고객 경험을 위해 유지합니다. |
| 휴면 전환 일시 | dormantAt | 상태가 DORMANT이면 필수. 휴면이 된 시각. 휴면 중에는 마케팅 발송 대상에서 빠집니다. |
| 정지 일시 | suspendedAt | 상태가 SUSPENDED이면 필수. 이용 정지 시각. |
| 탈퇴 완료 일시 | withdrawnAt | 상태가 WITHDRAWN이면 필수. 개인정보를 파기한 시각입니다. 고객 행 자체는 주문 기록 보존을 위해 지우지 않습니다. |
| 합쳐진 회원 ID | mergedIntoCustomerId | [FK→Customer] 비회원 행만 사용. 이 비회원 주문을 가져간 회원의 고객 ID입니다. 비회원 행을 지우지 않고 남겨서 "비회원으로 샀다"는 사실을 보존하고, 회원의 주문 목록은 본인 행 + 합쳐진 비회원 행으로 보여 줍니다. |
| 합쳐진 일시 | mergedAt | 상태가 MERGED이면 필수. 회원 계정으로 가져간 시각. |
| 생성 일시 | createdAt | 필수. 이 행이 생긴 시각. 회원은 가입 시작 시각, 비회원은 주문서 작성 시각입니다. |
| 수정 일시 | updatedAt | 필수. 마지막으로 이 행을 고친 시각. |

제약조건
- `customerKind = GUEST`이면 memberType·gradeId·joinedAt·joinChannel 비움, isLifetimeMember = false, status ∈ (ACTIVE, MERGED). MEMBER이면 위 칸이 필수이고 status ∈ (ACTIVE … WITHDRAWN). (CHECK)
- status가 DORMANT/SUSPENDED/WITHDRAWN/MERGED이면 각각의 일시 칸 필수. (CHECK)
- 상태가 바뀌면 statusChangedAt도 새 값이어야 하고, 트리거가 `CustomerStatusHistory`에 1줄을 자동 기록합니다. 허용 전이: ACTIVE↔DORMANT, ACTIVE↔SUSPENDED, ACTIVE/DORMANT→WITHDRAW_PENDING→(ACTIVE | WITHDRAWN). WITHDRAWN과 MERGED는 끝 상태입니다. (트리거)
- 회원 유형이 BUSINESS면 `CustomerBusiness`, FOREIGNER면 `CustomerForeigner` 행이 있어야 가입 완료(ACTIVE)가 됩니다. (트리거)
- 비회원 행에는 Verification·Credential·Social·Business·Foreigner·BodyProfile·Address·GradeHistory 행을 만들 수 없습니다. (각 테이블 트리거)
- mergedIntoCustomerId는 MEMBER 행만 가리킬 수 있고 자기 자신은 안 됩니다. 한 번 정하면 바꿀 수 없습니다. (트리거)
- 고객 행은 지울 수 없습니다(주문·결제 증빙). (트리거)

예시
| id | customerNo | customerKind | memberType | status | gradeId | isLifetimeMember | mergedIntoCustomerId |
|---|---|---|---|---|---|---|---|
| 1 | C4829103756 | MEMBER | BUSINESS | ACTIVE | 2 | false | |
| 2 | C9013377210 | GUEST | | MERGED | | false | 1 |

### 4-2. 고객 개인정보 `CustomerProfile`
이름·연락처처럼 **사람을 알아볼 수 있는 정보**만 따로 모은 테이블입니다(고객 1명당 1행). 분리하는 이유는 세 가지입니다. ① 이 테이블만 암호화·접근 제한을 걸면 됩니다. ② 탈퇴·파기 때 이 행만 비우면 됩니다. ③ 목록·통계 쿼리가 개인정보를 읽지 않게 됩니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 고객 ID | customerId | [PK, FK→Customer] 고객과 1:1. |
| 이름(암호화) | nameEnc | 필수(파기 후 비움). 회원은 본인인증 결과의 실명을 그대로 넣어 고객이 마음대로 바꿀 수 없습니다. 비회원은 주문서에 적은 이름입니다. AES-256-GCM 암호문(`v1:…`)만 허용합니다. |
| 휴대폰(암호화) | phoneEnc | 필수(파기 후 비움). 회원은 본인인증한 번호이고, 바꾸려면 다시 본인인증해야 합니다. 주문·배송 알림을 보내는 번호입니다. |
| 휴대폰 검색값 | phoneHash | 필수(파기 후 비움). 휴대폰 번호를 비밀키로 HMAC한 값입니다. 암호문은 같은 번호라도 매번 달라서 검색이 안 되기 때문에, 고객센터의 "전화번호로 고객 찾기"용으로 둡니다. 원래 번호로 되돌릴 수 없습니다. |
| 이메일(암호화) | emailEnc | 필수(파기 후 비움). 주문 확인·영수증 메일 주소. 소셜 로그인 이메일과 다를 수 있습니다. |
| 이메일 검색값 | emailHash | 필수(파기 후 비움). 이메일 HMAC. 이메일로 고객 찾기, 아이디 찾기에 씁니다. |
| 이메일 인증 일시 | emailVerifiedAt | 선택. 룩플처럼 가입 후 인증 메일 링크를 누른 시각. 인증 전 이메일로는 마케팅 메일을 보내지 않습니다(잘못 입력한 남의 주소일 수 있음). |
| 성별 | gender | 선택. `MALE` / `FEMALE` / `UNDISCLOSED`. 선택 개인정보 수집에 동의한 경우만 입력합니다. 상품 추천·통계용입니다. 본인인증 결과의 성별을 자동으로 넣지 않는 것은 최소 수집 원칙 때문입니다. |
| 생년월일(암호화) | birthDateEnc | 선택. 선택 동의 시에만 입력. 연령대 통계용입니다. |
| 생일 월 | birthMonth | 선택. 1~12. 생일 쿠폰을 매달 발급할 때 암호문을 풀지 않고 찾기 위한 평문입니다. 월만으로는 사람을 특정할 수 없어 평문으로 둡니다. |
| 개인정보 파기 일시 | piiPurgedAt | 선택. 탈퇴 완료나 비회원 보관기간(5년) 만료로 위 개인정보 칸을 비운 시각. 파기 후에는 암호문 칸이 모두 비어 있어야 합니다. |
| 수정 일시 | updatedAt | 필수. 마지막 수정 시각(휴대폰·이메일 변경 추적). |

제약조건
- *Enc 칸은 `v1:` 형식의 암호문만 허용합니다(평문 저장 차단 CHECK). birthMonth는 1~12입니다.
- piiPurgedAt이 있으면 모든 *Enc·*Hash 칸이 비어 있어야 하고, 없으면 이름·휴대폰·이메일이 필수입니다. (CHECK)
- 선택 정보(gender·birthDateEnc·birthMonth)는 선택 개인정보 동의(`PRIVACY_OPTIONAL`)가 유효할 때만 넣을 수 있습니다. 동의를 철회하면 앱이 비우고, `db:verify`가 어긋난 행을 보고합니다(트리거로 다른 테이블 최신 상태까지 보기에는 비용이 커서 검증 스크립트로 확인).

### 4-3. 본인인증 기록 `CustomerVerification`
본인인증(휴대폰·아이핀)을 **할 때마다 1줄**씩 남깁니다. 가입 때 한 인증이 "이 계정의 주인"을 정하고, 휴면 해제·휴대폰 변경·비밀번호 찾기 때 한 인증은 같은 사람인지 대조하는 데 씁니다. 주민번호·외국인등록번호는 받지 않고, 인증 업체가 주는 **CI(연계정보)** 를 다시 해시해서 저장합니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 인증 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. 회원만(비회원 불가). |
| 인증 목적 | purpose | 필수. `SIGNUP`(가입) / `DORMANT_RELEASE`(휴면 해제) / `PHONE_CHANGE`(휴대폰 변경) / `PASSWORD_RESET`(비밀번호 찾기) / `GUEST_CLAIM`(비회원 주문 가져오기). 목적마다 검사 규칙이 달라서 구분합니다. |
| 인증 수단 | method | 필수. `PHONE`(휴대폰) / `IPIN`(아이핀). 룩플과 같은 두 가지입니다. |
| 인증 업체 | provider | 필수. 예: `NICE`, `KCB`, `TEST`(개발용 가짜 인증). 업체를 바꿔도 기록이 섞이지 않게 남깁니다. |
| 인증 거래번호 | providerTxId | [UK] 필수. 인증 업체가 준 거래 번호. 같은 인증 결과를 두 번 써서 가입하는 재사용 공격을 막습니다. |
| CI 해시 | ciHash | 필수. 인증 업체가 주는 CI(사람마다 평생 같은 88바이트 값)를 우리 비밀키로 HMAC한 값입니다. **1인 1계정**의 열쇠입니다. CI 원문은 저장하지 않습니다(유출되면 다른 사이트 계정까지 연결될 수 있음). |
| 내·외국인 | nationalityType | 필수. `KOREAN` / `FOREIGNER`. 인증 결과에서 받습니다. 외국인 회원 유형이 실제 외국인인지 확인합니다. |
| 14세 이상 확인 | isOver14 | 필수, 항상 true. 인증 결과의 생년월일로 계산합니다. 14세 미만이면 행을 만들기 전에 가입을 막습니다. 생년월일 자체는 여기에 저장하지 않습니다(필요하면 선택 동의로 Profile에). |
| 인증 일시 | verifiedAt | 필수. 인증을 완료한 시각. |
| 접속 IP(가림) | ipMasked | 선택. `123.45.*.*`처럼 가린 IP. 부정 가입 조사용입니다. |

제약조건
- `purpose = SIGNUP`인 행의 ciHash는 **살아 있는 회원**(status가 WITHDRAWN이 아님) 사이에서 중복 불가입니다. 같은 사람의 두 번째 가입을 막습니다. (트리거. SQLite 부분 유니크 인덱스로는 다른 테이블의 상태를 볼 수 없어서 트리거를 씁니다.)
- SIGNUP이 아닌 인증은 ciHash가 그 고객의 SIGNUP 인증과 같아야 합니다(다른 사람이 대신 인증하는 것 차단). (트리거)
- memberType = FOREIGNER인 고객의 SIGNUP 인증은 nationalityType = FOREIGNER, 그 외 회원 유형은 KOREAN이어야 합니다. (트리거)
- isOver14 = true만 허용하고(CHECK), 비회원 고객에는 넣을 수 없습니다. 행은 추가만 가능합니다(수정·삭제 금지 트리거). 단 탈퇴 파기 때 ciHash는 비웁니다(재가입 제한은 탈퇴 테이블의 별도 해시로).

### 4-4. 자체 로그인 계정 `CustomerCredential`
쇼핑몰에서 직접 만든 **아이디·비밀번호**입니다. 소셜로만 가입한 회원은 이 행이 없습니다. 비밀번호를 고객 테이블에 두지 않는 이유는 소셜 전용 회원이 많아 빈칸이 생기고, 인증 정보는 접근을 가장 엄격하게 막아야 하기 때문입니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 고객 ID | customerId | [PK, FK→Customer] 회원 1명당 자체 계정 최대 1개. |
| 아이디 | loginId | [UK] 필수. 영문 소문자·숫자 4~16자(룩플 규칙). 대소문자 혼동을 막기 위해 소문자로만 저장합니다. 탈퇴해도 다른 사람이 같은 아이디를 다시 쓰지 못하게 남겨 둡니다(사칭 방지). |
| 비밀번호 해시 | passwordHash | 필수. 비밀번호는 원문을 저장하지 않고 `scrypt`(또는 argon2id) 해시만 저장합니다. 형식 `s1:소금값:해시`. 탈퇴 시 비웁니다. 룩플 규칙(4~16자)은 약해서 **8자 이상, 영문·숫자·특수문자 중 2종 이상**을 제안합니다(정할 것 참고). |
| 비밀번호 변경 일시 | passwordChangedAt | 필수. 마지막 변경 시각. 오래된 비밀번호 변경 안내, 변경 후 다른 기기 로그아웃 기준으로 씁니다. |
| 연속 실패 횟수 | failedCount | 필수, 기본 0. 비밀번호를 연속으로 틀린 횟수. 성공하면 0으로 돌아갑니다. |
| 잠금 해제 일시 | lockedUntil | 선택. 5회 연속 실패하면 30분 잠금. 이 시각 전에는 맞는 비밀번호로도 로그인할 수 없습니다(무작위 대입 방어). |
| 마지막 실패 일시 | lastFailedAt | 선택. 실패 횟수를 일정 시간 뒤 초기화할 때 기준이 됩니다. |
| 생성 일시 | createdAt | 필수. 자체 계정을 만든 시각. 소셜로 가입한 뒤 나중에 아이디를 추가한 경우도 알 수 있습니다. |

제약조건
- loginId는 `^[a-z0-9]{4,16}$`, failedCount ≥ 0, passwordHash는 `s1:` 형식입니다(탈퇴 후 비움). (CHECK)
- 회원만 만들 수 있습니다(비회원 고객이면 거부, 트리거).
- 자체 계정 삭제는 연결된 소셜 계정이 1개 이상 남아 있을 때만 가능합니다. 마지막 로그인 수단은 없앨 수 없습니다. (트리거)

### 4-5. 소셜 로그인 연결 `CustomerSocialAccount`
카카오·네이버·구글·애플 계정과의 연결입니다. 한 회원이 여러 개를 연결할 수 있어서 1:N입니다. 외부 회사의 **사용자 번호**로 사람을 알아보고, 이메일로는 알아보지 않습니다(이메일은 바뀔 수 있음). 지난번에 문제가 됐던 **접근 토큰은 저장하지 않습니다**. 로그인 확인이 끝나면 쓸 일이 없기 때문입니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 연결 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. 회원만. |
| 제공자 | provider | 필수. `KAKAO` / `NAVER` / `GOOGLE` / `APPLE` / `GITHUB`(개발 환경 전용). 새 회사를 붙이면 값만 추가합니다. |
| 제공자 사용자번호 | providerUserId | 필수. 그 회사가 정한 사용자 고유번호(예: 카카오 회원번호). 로그인할 때 이 값으로 회원을 찾습니다. |
| 연결 당시 이메일(암호화) | providerEmailEnc | 선택. 연결할 때 제공자가 준 이메일. 고객센터에서 "어느 카카오 계정으로 가입했나요?" 같은 문의에 답할 때 씁니다. |
| 연결 일시 | linkedAt | 필수. 연결한 시각. |
| 마지막 로그인 일시 | lastLoginAt | 선택. 이 수단으로 마지막 로그인한 시각. 마이페이지의 "연결된 계정" 화면에 보여 줍니다. |
| 해제 일시 | unlinkedAt | 선택. 연결을 끊은 시각. 행을 지우지 않고 남겨 "언제 무엇이 연결돼 있었나"를 보존합니다. |

제약조건
- (provider, providerUserId)는 **해제되지 않은 연결 중에서** 중복 불가입니다. 같은 카카오 계정이 두 회원에 붙지 못합니다. (부분 유니크 인덱스 `WHERE unlinkedAt IS NULL`)
- 한 회원은 provider마다 살아 있는 연결이 1개뿐입니다. (부분 유니크)
- 해제할 때 그 회원의 다른 로그인 수단(자체 계정 또는 다른 소셜)이 없으면 거부합니다. (트리거)
- 비회원 고객이면 거부하고, GITHUB는 운영 환경에서 앱이 막습니다(DB는 허용, 설정으로 차단).

### 4-6. 사업자 정보 `CustomerBusiness`
**사업자 회원**(개인사업자·법인사업자·기관단체)만 1행을 갖습니다. 사업자 회원을 받는 목적은 **세금계산서 발행**과 **단체 구매**입니다. 사업자번호는 국세청 조회로 진짜인지, 영업 중인지 확인합니다. 로그인하는 사람(담당자)의 이름·연락처는 `CustomerProfile`에 있습니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 고객 ID | customerId | [PK, FK→Customer] memberType = BUSINESS인 회원만. |
| 사업자 구분 | businessType | 필수. `SOLE_PROPRIETOR`(개인사업자) / `CORPORATION`(법인사업자) / `ORGANIZATION`(기관·단체). 룩플의 세 가지 구분입니다. 구분마다 필수 칸이 달라서 둡니다. |
| 상호(기관명) | businessName | 필수. 사업자등록증의 상호, 기관·단체는 고유번호증의 단체명. 세금계산서 "공급받는 자"에 찍힙니다. |
| 사업자등록번호 | businessNo | 필수. 숫자 10자리(하이픈 없이 저장). 기관·단체는 고유번호(형식이 같음)를 넣습니다. 국세청 조회와 세금계산서 발행의 열쇠입니다. 공개 정보라 평문으로 둡니다. |
| 대표자명 | representativeName | 필수. 국세청 진위확인에 대표자명이 필요해서 받습니다. 세금계산서에도 들어갑니다. |
| 개업일자 | openingDate | 필수. `YYYY-MM-DD`. 국세청 진위확인 필수 항목입니다. |
| 법인등록번호 | corporateNo | 법인사업자만 필수, 나머지는 비움. 숫자 13자리. 룩플이 법인에게 따로 받는 번호입니다. 법인 번호는 개인정보가 아닙니다. |
| 업태 | businessCategory | 필수. 예: 도소매. 세금계산서 기재 항목입니다(룩플 필수 항목). |
| 종목 | businessItem | 필수. 예: 의류. 세금계산서 기재 항목입니다. |
| 세금계산서 이메일(암호화) | taxInvoiceEmailEnc | 필수. 전자세금계산서를 받을 이메일. 담당자 개인 메일과 다른 회계팀 주소인 경우가 많아 따로 둡니다. |
| 국세청 사업자 상태 | ntsStatus | 필수. `ACTIVE`(계속사업자) / `SUSPENDED`(휴업) / `CLOSED`(폐업). 국세청 상태조회 결과입니다. 폐업이면 가입을 막고, 가입 후 폐업이면 세금계산서를 발행하지 않습니다. |
| 과세 유형 | ntsTaxType | 필수. `GENERAL`(일반과세) / `SIMPLIFIED`(간이과세) / `TAX_FREE`(면세) / `NON_PROFIT`(비영리·고유번호). 국세청이 알려 주는 값입니다. 세금계산서 발행 가능 여부가 달라집니다. |
| 진위확인 일시 | ntsVerifiedAt | 필수. 가입 때 국세청 진위확인에 성공한 시각입니다(번호·대표자명·개업일 일치). |
| 마지막 상태조회 일시 | ntsCheckedAt | 필수. 휴·폐업 여부를 마지막으로 다시 조회한 시각. 세금계산서 발행 전이나 월 1회 작업이 갱신합니다. |
| 생성 일시 | createdAt | 필수. |
| 수정 일시 | updatedAt | 필수. 상호·업태 변경을 추적합니다. |

제약조건
- businessNo는 숫자 10자리이고 **사업자번호 검증 공식(마지막 자리 검증수)** 에 맞아야 합니다. corporateNo는 13자리 숫자이고, `businessType = CORPORATION`일 때만 필수·허용입니다. (CHECK / 트리거)
- 살아 있는 사업자 회원 사이에서 businessNo 중복을 금지합니다(룩플의 "중복확인"). 한 회사가 여러 담당자 계정을 원하면 정할 것으로 남깁니다. (트리거)
- ntsStatus = CLOSED인 상태로는 가입 완료(ACTIVE) 전환을 막습니다. (트리거)
- Customer.memberType = BUSINESS가 아니면 행을 만들 수 없습니다. (트리거)

### 4-9. 배송지 주소록 `CustomerAddress`
회원이 **저장해 둔 배송지**입니다. 주문할 때 여기서 골라 주문에 **복사(스냅샷)** 하므로, 주소록을 고치거나 지워도 지난 주문의 배송지는 바뀌지 않습니다. 비회원은 주문서에 직접 적고 주소록은 없습니다.

| 논리명 | 물리명 | 컬럼 설명 |

| 배송지 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. 회원만. |
| 배송지 이름 | label | 필수. 예: `집`, `회사`. 고객이 목록에서 구분하는 이름입니다. 최대 20자. |
| 받는 분(암호화) | recipientEnc | 필수. 회원 본인과 다를 수 있습니다(선물, 가족). |
| 연락처(암호화) | phoneEnc | 필수. 택배 기사가 연락하는 번호. |
| 우편번호 | zipCode | 필수. 5자리 평문. 제주·도서산간 추가 배송비 판단에 쓰고, 이것만으로는 사람을 특정할 수 없어 평문으로 둡니다. |
| 기본 주소(암호화) | address1Enc | 필수. 도로명 주소(주소 검색 결과). |

| 기본 배송지 여부 | isDefault | 필수. 주문서를 열면 먼저 선택되는 배송지. 한 회원에 1개만 허용합니다. |

- 탈퇴하면 모두 삭제합니다. 주문에는 이미 복사본이 있어서 지워도 주문 기록이 깨지지 않습니다. 주문 테이블은 이 테이블을 FK로 묶지 않거나 SetNull로 둡니다(주문 도메인에서 결정).

### 4-10. 약관 버전 `TermsVersion`
이용약관·개인정보 동의서는 **내용이 바뀔 때마다 새 버전**을 만듭니다. "이 고객이 어떤 문구에 동의했나"를 나중에 증명하려면, 동의 기록이 그 당시 문구를 가리켜야 하기 때문입니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 약관 버전 ID | id | [PK] 자동 증가. |
| 약관 종류 | termsType | 필수. `TERMS_OF_SERVICE`(이용약관, 필수) / `PRIVACY_REQUIRED`(개인정보 수집·이용, 필수) / `PRIVACY_OPTIONAL`(선택 정보 수집: 성별·생일·체형) / `MARKETING`(광고성 정보 수신, 선택) / `NIGHT_PUSH`(야간 광고 푸시, 선택) / `GUEST_PRIVACY`(비회원 주문 개인정보, 비회원 필수). 룩플의 필수 2개·선택 항목을 우리 수집 범위에 맞춰 정리했습니다. |
| 버전 | version | 필수. 예: `2026-11-01`. 같은 종류 안에서 중복 불가입니다. |
| 제목 | title | 필수. 화면에 보이는 제목. |
| 본문 | content | 필수. 그 버전의 전체 문구. 나중에 "그때 무슨 내용에 동의했나"를 보여 주려면 본문 자체를 보관해야 합니다. 공개 후에는 수정할 수 없습니다. |
| 필수 여부 | isRequired | 필수. 동의하지 않으면 가입(또는 비회원 주문)이 안 되는 항목인지. 종류로 정해지지만 화면 표시와 검사에 바로 쓰려고 둡니다. |
| 시행 일시 | effectiveFrom | 필수. 이 버전이 적용되기 시작하는 시각. 약관 변경은 시행 7일 전(불리한 변경은 30일 전) 공지가 필요해서 미래 시각으로 미리 등록할 수 있습니다. |
| 종료 일시 | effectiveTo | 선택. 다음 버전이 시행되면 채웁니다. 비어 있으면 현재 버전입니다. |
| 생성 일시 | createdAt | 필수. |

제약조건
- (termsType, version) 중복 불가. 같은 종류의 시행 기간은 겹칠 수 없습니다(현재 버전이 항상 1개). 동의 기록이 하나라도 있는 버전은 본문·필수 여부를 고칠 수 없습니다. (UK / 트리거)

### 4-11. 동의 이력 `CustomerConsent`
동의와 철회를 **일어날 때마다 1줄씩 추가**하는 기록부입니다(수정·삭제 금지). 분쟁이나 감독기관 점검 때 "언제, 어떤 문구에, 어떤 화면에서 동의했나"를 증명합니다. 현재 동의 상태는 종류별 가장 최근 줄로 판단하고, 마케팅은 빠른 조회를 위해 4-12에 따로 둡니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 이력 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. 비회원도 `GUEST_PRIVACY` 동의를 여기에 남깁니다(전에는 비회원 주문 테이블에 있던 것을 고객 도메인으로 모음). |
| 약관 버전 ID | termsVersionId | [FK→TermsVersion] 필수. 동의한 문구의 버전. |
| 동작 | action | 필수. `AGREE`(동의) / `WITHDRAW`(철회). 필수 약관은 철회할 수 없고, 철회하려면 탈퇴해야 합니다. |
| 경로 | source | 필수. `SIGNUP`(가입 화면) / `MY_PAGE`(마이페이지) / `CHECKOUT`(주문서) / `RECONFIRM`(2년 재확인 응답) / `ADMIN`(고객센터 대리 처리). |
| 처리 관리자 | processedById | 선택. source = ADMIN이면 필수. 전화로 철회 요청을 받아 직원이 처리한 경우 누가 처리했는지 남깁니다. |
| 발생 일시 | occurredAt | 필수. |
| 접속 IP(가림) | ipMasked | 선택. 본인이 화면에서 동의했다는 보조 증거입니다. |

제약조건
- 추가만 가능합니다(수정·삭제 금지 트리거). 필수 약관(isRequired) 버전에는 WITHDRAW를 넣을 수 없습니다(트리거). 회원 가입 완료(ACTIVE) 시점에 현재 시행 중인 필수 약관 2개(이용약관·개인정보)에 AGREE가 있어야 합니다(트리거).
- MARKETING·NIGHT_PUSH 동의·철회는 4-12의 현재 상태와 항상 같이 바뀝니다(같은 트랜잭션, `db:verify`로 일치 확인).

### 4-12. 마케팅 수신 설정 `CustomerMarketingPreference`
광고를 보낼 때마다 동의 이력 전체를 뒤지지 않도록 **채널별 현재 상태**를 1행씩 둡니다. 법에서 정한 **2년마다 재확인 통지**를 언제 보냈는지도 여기에 기록합니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 고객 ID | customerId | [PK 1/2, FK→Customer] 회원만. |
| 채널 | channel | [PK 2/2] `SMS` / `EMAIL` / `PUSH`(앱 알림). 룩플은 SMS·이메일이고, 앱을 대비해 푸시를 추가했습니다. 채널마다 따로 동의·철회할 수 있습니다. |
| 수신 동의 여부 | isAgreed | 필수. 현재 이 채널로 광고를 받는지. 발송 대상 추출에 바로 씁니다. |
| 동의 일시 | agreedAt | 동의 중이면 필수. 마지막으로 동의한 시각. 2년 재확인 주기의 시작점입니다. |
| 철회 일시 | withdrawnAt | 선택. 마지막으로 철회한 시각. |
| 야간 수신 동의 | nightAgreed | 필수, 기본 false. PUSH 채널만 의미가 있습니다. 21시~8시 광고 푸시는 별도 동의가 필요합니다. |
| 마지막 재확인 통지 일시 | lastReconfirmNoticeAt | 선택. "광고 수신에 동의한 상태입니다"라는 2년 주기 안내를 보낸 시각. 다음 통지 대상은 이 값(없으면 agreedAt)으로부터 2년이 지난 회원입니다. |
| 수정 일시 | updatedAt | 필수. |

제약조건
- isAgreed = true이면 agreedAt 필수입니다. nightAgreed = true는 channel = PUSH이고 isAgreed = true일 때만 허용합니다. (CHECK)
- 고객 상태가 DORMANT·WITHDRAWN이면 발송하지 않는데, 이것은 발송 쿼리 조건으로 처리합니다. 동의 상태를 지우면 휴면 해제 후 다시 물어야 하므로 지우지 않습니다.

### 4-13. 회원 등급 `CustomerGrade`
등급의 **기준과 혜택**입니다. 등급별 숫자를 코드에 박아 두지 않고 테이블에 두어, 기준이 바뀌어도 코드를 고치지 않게 합니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 등급 ID | id | [PK] 자동 증가. |
| 등급 코드 | code | [UK] 필수. 예: `WELCOME`, `SILVER`, `GOLD`, `VIP`. 코드에서 등급을 가리킬 때 씁니다. |
| 등급명 | name | 필수. 화면 표시 이름. |
| 등급 순위 | level | [UK] 필수. 1이 가장 낮습니다. "GOLD 이상에게 쿠폰 발급" 같은 비교에 씁니다. |
| 최소 구매 금액 | minPurchaseAmount | 필수. 산정 기간 동안 구매 확정된 결제 금액 합계가 이 금액 이상이면 이 등급입니다(원). 기본 등급은 0. |
| 최소 구매 횟수 | minOrderCount | 필수, 기본 0. 금액과 함께 보는 조건(둘 다 만족). 한 번에 큰 금액으로 등급만 올리는 것을 막고 싶을 때 씁니다. |
| 산정 기간(개월) | evaluationMonths | 필수, 기본 12. 최근 몇 개월 구매로 산정하는지. |
| 적립률(%) | pointRate | 필수. 구매 확정 시 포인트 적립 비율(포인트 도메인이 사용). 0~20. |
| 기본 등급 여부 | isDefault | 필수. 가입하면 받는 등급. 정확히 1개만 true입니다. |
| 사용 여부 | isActive | 필수. 등급을 없앨 때 지우지 않고 끕니다(이력이 이 등급을 가리키므로). |
| 생성 일시 | createdAt | 필수. |
| 수정 일시 | updatedAt | 필수. |

제약조건
- level이 높을수록 minPurchaseAmount가 같거나 커야 합니다. 이력이나 회원이 쓰는 등급은 삭제할 수 없습니다. isDefault = true는 정확히 1개입니다. (트리거 / 부분 유니크)

### 4-14. 등급 변경 이력 `CustomerGradeHistory`
등급이 **언제, 왜, 어떤 근거로** 바뀌었는지 남깁니다. "왜 내 등급이 내려갔나요?" 문의에 산정 금액과 기간으로 답할 수 있게 합니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 이력 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. 회원만. |
| 이전 등급 | fromGradeId | [FK→CustomerGrade] 선택. 가입 시 첫 등급이면 비웁니다. |
| 변경 등급 | toGradeId | [FK→CustomerGrade] 필수. |
| 변경 사유 | reason | 필수. `SIGNUP`(가입) / `PERIODIC`(정기 산정) / `ADMIN`(관리자 조정) / `GUEST_MERGE`(비회원 주문 합산으로 재산정). |
| 산정 구매 금액 | evaluatedAmount | 정기 산정이면 필수. 산정에 쓴 구매 금액 합계. |
| 산정 구매 횟수 | evaluatedOrderCount | 정기 산정이면 필수. |
| 산정 기간 시작 | periodFrom | 정기 산정이면 필수. |
| 산정 기간 끝 | periodTo | 정기 산정이면 필수. |
| 처리자 | changedById | 선택. 사유가 ADMIN이면 필수(관리자 ID). 그 외에는 작업 이름. |
| 메모 | memo | 선택. 관리자 조정 사유 등. |
| 변경 일시 | changedAt | 필수. |

제약조건
- 추가만 가능합니다. `Customer.gradeId`를 바꾸려면 같은 시각에 이 테이블에 toGradeId가 그 값인 행이 먼저 있어야 합니다(트리거). PERIODIC이면 산정 칸 4개가 필수이고 periodFrom < periodTo입니다(CHECK).

### 4-15. 상태 변경 이력 `CustomerStatusHistory`
`Customer.status`가 바뀔 때마다 **트리거가 자동으로 1줄** 남깁니다. 지난 주문 피드백에서 지적하신 "변경자가 없다"를 반영해 역할과 처리자 ID, 사유 코드를 모두 남깁니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 이력 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. |
| 이전 상태 | fromStatus | 선택. 처음 생성이면 비웁니다. |
| 변경 상태 | toStatus | 필수. |
| 사유 코드 | reasonCode | 필수. Customer.statusReasonCode를 복사합니다. |
| 변경 주체 | changedByType | 필수. CUSTOMER / ADMIN / SYSTEM. |
| 처리자 | changedById | 선택. ADMIN이면 필수(관리자 ID), SYSTEM이면 작업 이름. |
| 메모 | memo | 선택. |
| 변경 일시 | changedAt | 필수. Customer.statusChangedAt과 같은 값. |

제약조건
- 앱은 이 테이블에 직접 쓰지 않습니다. Customer의 상태 칸을 바꾸면 트리거가 씁니다. 추가만 가능하고 수정·삭제는 금지입니다.

### 4-16. 탈퇴 신청 `CustomerWithdrawal`
탈퇴는 **신청 → 7일 유예(철회 가능) → 완료(개인정보 파기)** 순서로 진행합니다. 완료 뒤에도 같은 사람이 30일 안에 다시 가입해 가입 혜택을 또 받지 못하게, 파기한 CI 대신 **재가입 제한용 해시**를 남깁니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 탈퇴 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 필수. 회원만. 철회 후 다시 신청할 수 있어서 1:N입니다. |
| 진행 상태 | status | 필수. `REQUESTED`(유예 중) / `CANCELED`(본인 철회) / `COMPLETED`(완료). |
| 탈퇴 사유 | reasonCode | 필수. `LOW_USAGE` / `PRIVACY` / `PRODUCT` / `DELIVERY` / `SERVICE` / `REJOIN` / `OTHER`. 서비스 개선 통계용입니다. |
| 사유 상세 | reasonText | 선택. 고객이 직접 쓴 내용(최대 500자). |
| 신청 일시 | requestedAt | 필수. |
| 완료 예정 일시 | scheduledAt | 필수. 신청 + 7일. 이 시각에 작업이 탈퇴를 완료합니다. |
| 철회 일시 | canceledAt | 상태가 CANCELED이면 필수. |
| 완료 일시 | completedAt | 상태가 COMPLETED이면 필수. |
| 재가입 제한 해시 | rejoinBlockHash | 완료 시 필수. CI를 **재가입 제한 전용 비밀키**로 HMAC한 값입니다. 가입용 ciHash와 키를 달리해서, 이 값만으로는 과거 회원 정보와 연결할 수 없게 합니다. |
| 재가입 제한 종료 일시 | rejoinBlockedUntil | 완료 시 필수. 완료 + 30일. 이 시각 전에는 같은 사람(같은 CI)이 가입할 수 없습니다. |

제약조건
- 한 고객에 REQUESTED는 1개만 허용합니다(부분 유니크). 신청은 미결제·배송 중·반품 진행 중 주문이 있으면 막습니다(주문 도메인과 연결되는 규칙, 트리거). 완료되면 Customer.status = WITHDRAWN과 개인정보 파기가 같은 트랜잭션에서 일어나야 합니다(트리거 검사).

### 4-17. 로그인 기록 `CustomerLoginHistory`
로그인 **성공과 실패를 모두** 남깁니다. 계정 도용 의심 시 조사하거나 마이페이지의 "최근 로그인 기록"을 보여 줄 때 씁니다. 3개월 보관 후 지웁니다.

| 논리명 | 물리명 | 컬럼 설명 |
|---|---|---|
| 기록 ID | id | [PK] 자동 증가. |
| 고객 ID | customerId | [FK→Customer] 선택. 없는 아이디로 시도한 실패는 고객을 알 수 없어 비웁니다. |
| 로그인 수단 | method | 필수. `PASSWORD` / `KAKAO` / `NAVER` / `GOOGLE` / `APPLE` / `GITHUB`. |
| 결과 | result | 필수. `SUCCESS` / `WRONG_PASSWORD` / `UNKNOWN_ID` / `LOCKED` / `SUSPENDED`(정지 회원 차단) / `DORMANT`(휴면이라 해제 화면으로) / `REJOIN_BLOCKED`(재가입 제한). |
| 입력 아이디 해시 | loginIdHash | 선택. 아이디로 시도한 경우 입력값의 HMAC. 같은 아이디에 대한 대량 시도를 세는 데 씁니다(원문은 저장하지 않음). |
| 접속 IP(가림) | ipMasked | 선택. 사람이 보는 용도. |
| IP 해시 | ipHash | 선택. 같은 IP의 실패 횟수를 세는 용도(HMAC). |
| 브라우저 정보 | userAgent | 선택. 최대 300자. "새 기기에서 로그인" 판단과 마이페이지 표시용. |
| 발생 일시 | occurredAt | 필수. |

제약조건
- 추가만 가능합니다. result = SUCCESS이면 customerId가 필수입니다(CHECK). 3개월 지난 기록은 정리 작업이 삭제합니다.

## 6. 테스트 계획 (반영 단계에서)

1. **제약조건 거부 테스트**: 표마다 적은 CHECK·트리거를 어기는 SQL을 넣었을 때 DB가 거부하는지 확인합니다. 트리거를 지운 복사본에서는 같은 테스트가 실패하는지도 확인합니다.
2. **1인 1계정**: 같은 CI로 두 번 가입하면 거부, 탈퇴 후 30일 안 재가입 거부, 31일 뒤 허용.
3. **회원 유형**: 사업자인데 Business 행이 없거나, 외국인인데 내국인 인증이면 가입 완료 불가. 폐업 사업자 거부(가짜 국세청), 법인 아닌데 법인번호를 넣으면 거부.
4. **로그인 수단**: 자체 + 카카오 연결 → 카카오 해제 가능 → 자체 삭제 불가(마지막 수단). 같은 카카오 계정을 두 회원에 연결하면 거부. 5회 실패 잠금 후 30분 뒤 해제.
5. **비회원**: 비회원 행에 인증·등급·주소록을 넣으면 거부. 회원이 가져가면 MERGED 상태와 mergedIntoCustomerId 설정, 그 뒤 변경 불가.
6. **동의**: 필수 약관 철회 거부, 마케팅 동의·철회 이력과 현재 상태 일치, 2년 재확인 대상 추출, 야간 푸시는 푸시 동의 없이 불가.
7. **휴면·탈퇴**: 1년 미접속 휴면(평생회원 제외), 휴면 해제는 같은 CI 인증만, 탈퇴 유예 중 철회, 완료 시 개인정보 칸이 모두 비었는지.
8. **등급**: 이력 없이 등급 변경 거부, 정기 산정 결과와 이력의 산정 금액 일치.

## 7. 아직 정할 것 (사용자 피드백 필요)

1. **사업자 회원 담당자 여러 명**: 지금은 사업자번호당 회원 1명(중복 불가)입니다. 한 회사에서 여러 직원이 각자 계정을 쓰게 할지 정해야 합니다(그러면 C안처럼 회사 테이블 분리가 필요).
2. **비밀번호 규칙**: 룩플은 4~16자인데, 요즘 권장 기준(8자 이상, 2종 이상 조합)으로 올릴지.
3. **환불 계좌**: 룩플처럼 가입 때 받아 둘지, 지금처럼 환불할 때만 받을지.
4. **평생회원 혜택**: 룩플처럼 쿠폰을 주고 3개월 유지 의무를 둘지(쿠폰 도메인과 연결).
5. **비회원 개인정보 보관**: 비회원 행의 개인정보를 주문과 같이 5년 보관 후 파기하는 것으로 잡았습니다. 맞는지.
6. **등급 이름과 기준 금액**: WELCOME / SILVER / GOLD / VIP와 금액은 예시입니다.
7. **14세 미만**: 가입 차단으로 잡았습니다. 법정대리인 동의를 받아 가입시키려면 테이블이 하나 늘어납니다.
