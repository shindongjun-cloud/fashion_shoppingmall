### 이후 바뀐 것 (사용자 피드백)

- **출고·출고 상품·출고 상태 이력은 재고로 넘김.** 출고 테이블에 창고 일(포장, 상자 규격, 출고 일시)과 운송 일(송장, 배송 출발, 배송 완료)이 섞여 있었음. 배송 도메인에는 **배송**(출고와 1:1)과 배송 상태 이력을 둠. 정한 내용은 `02-tables.md` "재고로 넘길 초안".
- **배송 방식**: 기본 3가지(일반 택배, 새벽 배송, 당일 배송, 고객이 고름) + 예외 2가지(퀵, 직접 전달, 관리자만). 기차·고속버스는 퀵의 운송 수단. 퀵은 계약 없이 그때그때 부르므로 업체 이름은 글자로 적고, 기록은 **예외 배송 상세** 1개(퀵·직접 전달 합침). 칸 이름은 "퀵" 대신 "예외 배송 업체".
- **배송 방식(기준) / 배송 정책(운영 규칙) / 배송비 정책(금액)** 3개로 나눔. 바뀌는 때가 다름. 배송 구역은 배송 정책에 붙임.
- 예외 배송 상세는 정책이 아니라 배송에 연결(정책 = 메뉴판, 상세 = 영수증), 규칙은 배송 방식 기준.
- 이름: 택배사 → 배송 업체, 상태 코드 → **배송 추적 상태**("배송 업체 상태"는 업체의 사용·중지와 헷갈림), 배송비 부과 → **추가 배송비**, 일괄 작업 → **배송 엑셀 처리 기록 / 줄별 처리 결과**, 운임 → "운임 단가", 회수 지원 여부 → **회수 담당 여부**(사용 중 1개), 집하 마감 → **당일 집하 접수 마감 시각**(집하 시작 시각은 계산에 안 써서 두지 않음), 운송장 등록 일시 → **발급 일시**.
- 배송에 집하, 배송 출발, 도착 예정 시간대(시작·종료), 약속 도착, 배송 완료, 수령 장소, 완료 사진 주소, 미수령 신고.
- 상자 규격은 고객 배송비가 아니라 업체가 우리에게 청구하는 운임 기준. 옷이라 무게 칸은 삭제, 운송장에 **접수 상자 규격**.
- 고객 표시 여부 삭제(모든 단계를 보여 주고, 내부 코드는 문구로 바꿈). 안심번호 사용 여부는 운송장 → 배송 업체 계약.

## 추가 비용 대화(외부 ChatGPT) 검토

| 의견 | 판단 |
|---|---|
| 추가 비용은 배송 테이블이 아닌 별도 테이블 | 동의 → 추가 배송비 |
| 비용(왜 더 받나)과 결제(실제로 받았나)를 나눔 | 동의 → 추가 배송비 청구 ↔ 결제 |
| 추가 결제용 별도 주문(EXTRA-001) | **반대**: 주문에는 상품 계약 규칙(1개 1줄, 출고 기한, 연쇄 트리거, 최소 결제, 등급 실적)이 붙어 있음. 대신 원래 주문의 결제 행 + 결제 목적 구분 + 추가 배송비 청구ID |
| 주문 상태는 바꾸지 않음 | 동의(주문 = 처음 결제, 주문 상품 = 물건, 배송 = 물류, 추가 배송비 = 추가 비용) |
| 주문 상태 값에 PREPARING, SHIPPING 등 | 따르지 않음(물건 상태를 주문 상태에 섞지 않음) |
| 출고 상태에 RETURNED, RESHIPPING | 다르게 함: 반송은 회수, 재배송은 새 배송 |
| 미결제면 재배송 보류, 고객 동의 기록 | 동의 → 결제 기한, 안내·동의 일시·방법 |

## 시나리오로 찾은 문제 (관리자 처리 11개)

A 정상 배송, B 새벽 약속 위반, C 당일 중 재고 오류, D 송장 오입력, E 주소 오류 반송 → 고객 부담 재발송, F 사이즈 교환 + 간편 수거, G 회수 실패 3번 → 편의점 착불, H 신청 없는 반품, I 오배송 긴급 퀵, J 분실 → 재발송 → 업체 청구, K 월 운임 대사.

| # | 문제 | 해결 |
|---|---|---|
| 1 | 엑셀 실패 줄과 올린 사람을 남길 곳이 없음 | 배송 엑셀 처리 기록 + 줄별 처리 결과 |
| 2 | 업체에 신고한 상자 규격이 없음 | 운송장 접수 상자 규격 |
| 3 | 완료 때 수령 장소·사진이 없음 | 배송 수령 장소 구분, 완료 사진 주소 |
| 4 | "약속 위반"(늦게 도착)이 사고 구분에 없음 | 배송 사고 구분 추가 |
| 5 | 고객 선택과 다른 배송 방식의 이유가 없음 | 배송 방식 변경 사유 |
| 6 | 방식 변경 차액 항목이 없음 | 추가 배송비 항목 추가 |
| 7 | 배송 상태에 "반송"이 없음 | 배송 상태 값 추가 |
| 8 | 반송이 같은 송장으로 오면 회수가 따라갈 수 없음 | 회수 반송 추적 운송장ID |
| 9 | 결제 1번에 배송비 2건, 동의가 건마다 따로 | 추가 배송비 청구(머리) + 추가 배송비(항목), 결제는 청구를 가리킴 |
| 10 | 배송 처리 연락 기록을 남길 곳 | 주문 관리자 메모에 대상 배송·회수·사고ID(새 테이블 대신) |

시나리오 C(재고 오류)는 처음에 배송비 차액만 봤다가 사용자 지적으로 다시 정리: 고객에게 알리고 선택을 받음(기다림, 같은 상품 다른 옵션, 이 상품 취소, 전체 취소, 응답 없으면 이 상품 취소 + 환불 — 사용자 확정). 공급 의무는 주문의 일이라 주문 도메인에 **주문 상품 공급 문제**(17번)를 추가. 판매자 사유면 무료배송 기준 깨짐 배송비를 받지 않음. 공급 문제는 재고 등급(출고 전 하자 발견)과 연결되며, 원인 재고 기록 연결은 재고 때.

## 택배사가 관리할 것을 우리가 갖고 있나 (점검)

안심번호 사용 여부만 운송장 → 배송 업체 계약으로 옮김. 추적 이벤트(업체 조회 기간이 짧을 수 있음, 공급 기록 5년), 추적 상태 번역표, 도착 예정·사진(지연 감지와 안내), 운임 단가(청구 확인), 집하 마감(도착 예정 계산), 도서산간 목록(정책 버전 고정), 운임 청구 상세는 우리 규칙에 쓰는 복사본이라 유지.
