# 결제 2단계: 설계 방법과 결정 (2026-11-26)

사용자 질문 "결제 설계방법 모두 알려줘"로 시작했습니다. 이 파일은 채팅 답변 원문이 아니라 **결정과 그 이유의 요약**입니다. 테이블 정의는 `02-tables.md`, 검증 조건은 `03-integrity.md`에 있습니다.

- **사용자 목표**: "쉽고 빠르고 결제 양식은 간단하게. 허술하고 부족하고 보안이 약한 게 아니라 탄탄하게."
- **진행 순서(사용자 결정)**: ① 테이블 구조 설계 방법(1~21) → ② 기능·정책 → ③ 처리 방식. 처음에는 구조·기능·처리를 섞어 "설계 방법 17개"로 냈다가, 사용자 지적으로 나눴습니다.
- **용어 규칙(사용자 피드백)**: "남은 금액"처럼 줄여 말하지 않습니다. 이 결제에서 앞으로 더 돌려줄 수 있는 돈은 **취소 가능 금액**입니다.
- **경계**: 환불 금액 판단, 클레임, 환불 계좌, 지연배상금 지급은 환불 도메인에서 다룹니다. 결제 도메인은 결제사에 보낸 **결제 취소** 기록까지입니다.

## 1. 테이블 구조 결정 (1~21)

| # | 결정 지점 | 결정 | 이유 (요약) |
|---|---|---|---|
| 1 | 결제 한 행의 단위 | **③ 시도 단위**: 결제창을 열 때마다 1행 | 실패·포기·성공이 모두 남습니다. 주문 1 : 결제 N입니다. |
| 2 | 주문과의 연결 | **① 결제 → 주문 FK만** | 주문에 결제ID를 두면 재시도마다 고쳐야 합니다. |
| 3 | PK | **① 대리키** + 결제사 키 UK | 결제사 키는 결제창 인증 뒤에야 생깁니다. |
| 4 | 결제사 정보 | 처음에는 ② 결제사 구분 + MID 칸 → **결제사 가맹점 기준 테이블(③)로 변경** (PG를 토스로 확정한 뒤) | 계약 정보(수수료, 확인 번호, 취소 전용 상태)까지 관리해야 합니다. |
| 5 | 수단별 정보 | **② 공통 테이블 + 수단별 1:1 상세** | 아래 5번 "나누기 유지" 참고 |

| 7 | 복합 결제 | **① 결제 1건 = 수단 1개** (사용자 결정) | |

| 13 | 상태 관리 | **② 상태 칸 + 상태 이력** | |

| 15 | 결제사 응답 | **정리한 칸 + 결제사 통신 기록** | 원문은 가려서 1년 보관합니다. |

## 2. 기능·정책 결정

| 항목 | 결정 |
|---|---|
| PG사 | **토스페이먼츠** (사용자 확정). 이미 연동·테스트됨, 결제위젯이 약관 동의 화면까지 제공. 계약 전 수수료·정산 주기 비교는 **검증 필요** |
| 결제 수단 | 카드, 간편결제, 계좌이체, 가상계좌. **휴대폰 결제 제외** |
| 간편결제 | **토스페이만** (사용자 결정). 결제형만 사용하고 주문형은 제외. 카카오페이·네이버페이는 토스 관리 화면에서 끔 |
| 가상계좌 | 사용. 입금 기한 24시간(은행 점검 시간이면 그 전으로 당김, **검증 필요**). 주문 결제 만료와 재고 예약도 입금 기한까지 늘림. 주문 상태에는 "입금 대기"를 두지 않고 결제 상태로 보여 줌 |
| 에스크로 | 계좌이체·가상계좌에만 선택으로 제공. 진행 상태는 결제 에스크로 테이블에 둠 |
| 현금영수증 | 계좌이체·가상계좌에 발급. 결제 화면에 접혀 있고, 신청하지 않으면 자진발급(의무발행업종 여부 **검증 필요**) |
| 세금계산서 | 주문 상세에서 신청, 현금성 결제만, 현금영수증과 둘 중 하나. 가격이 부가세 포함가라 **10%를 더 받지 않음**. 사업자 정보는 신청한 건에만 저장(고객에 저장 안 함) |

| 결제 화면 관리 | **Q-1: 토스 위젯 관리 화면** + 결제사 가맹점의 결제 환경(테스트/실결제) |

## 3. 처리 방식 결정

| 지점 | 결정 |
|---|---|
| G 응답 없음 | **G-2**: 멱등키 + "확인 필요" 상태. 응답이 없으면 조회하고, 10분 안이면 같은 키로 재승인. 5xx 응답이면 조회한 뒤 새 키 "-rN"(토스는 오류 응답도 멱등키로 저장함) |
| H 웹훅 | **H-2**: 받은 내용은 기록만 하고, 결제사에 다시 조회한 결과로 반영 |
| K 결제 시작 | **K-2**: 앱 검사 + DB 최종 관문(주문 결제 대기, 금액 일치, 보호자 동의 유효). 결제를 시작하면 주문 만료와 재고 예약을 연장 |
| O 통신 기록 | **O-2**: 결제사 호출을 모두 가려서 기록, 1년 보관 |
| 프로시저 | **쓰지 않음**. DB 로직은 트리거 + CHECK·UK·FK, 나머지는 앱 쓰기 함수. 같은 로직이 두 곳에 생기지 않게 하고, 부르지 않으면 지켜지지 않는 문제를 피합니다. 대량 파기가 느려지면 그 작업만 다시 검토합니다. |

## 5. 다시 따져 본 구조

- **수단 상세: 나누기 유지.** 하나로 합쳐도 동작은 하지만 단점이 있습니다.
  - 카드 행에 가상계좌 칸 약 10개가 비고, 칸마다 NOT NULL을 걸 수 없어서 수단별 큰 CHECK를 써야 합니다.
  - 가상계좌 번호 같은 개인정보에 테이블 권한을 따로 줄 수 없습니다.
  - 수단을 추가할 때 큰 테이블을 바꿔야 합니다.

  합치기의 유일한 장점(토스페이 안 카드 결제가 한 행에 들어감)은 "간편결제 상세 + 카드 상세 2행 허용"으로 해결합니다.
- **에스크로는 이력 테이블이 아님.** 결제 1건의 지금 상태를 담는 1:1 상세(③)라서 같은 행을 고쳐 씁니다. 단계마다 일시 칸(배송 등록, 확인 요청, 확정, 거절, 정산)이 있어서 이력이 따로 필요 없습니다. 송장 재등록 기록은 배송 도메인에 남깁니다.
- **에스크로를 PG 테이블에 넣지 않음.** PG 테이블은 계약 1개가 1행이고, 에스크로는 결제 1건이 1행입니다. PG 테이블에는 에스크로 사용 여부와 확인 번호만 둡니다.
- **카드 상세 축소(사용자 동의).** 카드사가 처리하는 일이라 우리가 몰라도 되는 6칸을 지웠습니다.
  - 지운 칸: 매입사, 카드 소유자 구분, **할부 개월 수**, 무이자 여부, 카드사 즉시 할인 금액, 카드 청구 금액
  - 남긴 칸: 발급사, 가린 번호, 카드 구분, 승인번호

  고객은 토스 영수증에서 할부 정보를 볼 수 있습니다. 우리 돈으로 무이자 할부 행사를 하게 되면 다시 넣습니다.
- **결제 수단은 별도 테이블 없이** 결제의 수단 구분 칸(CHECK)으로 둡니다.

## 6. 고객 결제 시나리오에서 찾은 문제 (60개)

모든 문제의 해결은 테이블(칸) 또는 앱 처리 규칙으로 정했고, 6단계 검증 조건과 테스트 대상이 됩니다.

| 단계 | 번호 | 주요 문제 → 해결 |
|---|---|---|
| 결제 전 | 1~12 | 두 번 클릭·두 탭 → 진행 중 결제 UK. **뒤로 가기 후 다시 결제** → 결제사 키가 없는 예전 시도는 "포기", 있으면 먼저 조회. 금액 변동 → 시작 관문에서 다시 계산. 만료 직전 결제 → 만료·예약 연장. 미성년·정지 회원·비회원 세션 → 관문 검사. 약관 미리 체크 → 동의 일시 필수. 테스트 키로 운영 → 서버 시작 때 확인 |
| 결제창 | 13~18 | 창 닫기 → "포기"(토스가 주문번호를 안 주면 그 고객의 진행 중 결제로 찾음). 팝업 차단 → COOP 헤더. 한도 초과 등 → 고객 안내 구분. 앱 전환 후 못 돌아옴 → "확인 중" 화면 + 조회 + 웹훅. **인증 후 우리 서버 도착 전 창 닫기** → 승인 요청이 없어 돈이 안 나감(토스 폐기 시간 **검증 필요**). 카드 대입 공격 → IP 검색값으로 차단 |
| 승인 | 19~28 | 응답 없음 → 확인 필요 + 조회 + 같은 키. 5xx → 새 키. 금액 조작, 남의 결제키 → 서버 비교. 결제 중 주문 변경 → 금지(O-128). DB 저장 실패 → 보상 취소, 그것도 실패하면 확인 필요 + 알림 + 대사. 로그인 만료 → 같은 승인 주소로 이어서. 새로고침 → 결과만 보여 줌. 부가세 1원 차이 → 계산 규칙 하나 |
| 가상계좌 | 29~37 | 점검 시간 → 기한 당김. 기한 뒤 입금, 다른 금액 입금 → **검증 필요**, 대사 → 환불. 위조·중복 알림 → 검증값 + 중복 키. 만료 알림 없음 → 만료 작업. 입금 전 수단 변경·취소 → 계좌 폐기 후 새 시도. 입금 후 환불 → 환불 계좌 송금 |
| 간편결제 | 38~40 | 장애 → 다른 수단 안내. 충전금 + 카드 부분 취소 → 결제사 규칙(**검증 필요**). 간편결제 안 카드 → 상세 2행 허용 |

## 7. 데이터를 넣어 보고 추가한 칸

| 사례 | 추가한 칸 |
|---|---|
| ① 카드 한도 초과 → 다른 카드로 성공 | 결제: 요청 IP 검색값·표시값, 요청 기기 정보, 결제사 상태값 |
| ② 가상계좌 + 에스크로 → 반품 → 현금영수증 재발급 | 결제 취소: 결제사 취소 후 잔액 / 현금영수증: 신청 경로 구분 |
| ③ 토스페이 충전금 + 카드 → 부분 취소 | (기존 칸으로 처리) |
| ④ 사업자 세금계산서 → 반품 → 수정 발행 | 세금계산서: 사업자 상태 확인 결과·일시 |
| 대사 | 거래/정산 대사 구분, 승인·취소 건수·금액(우리·결제사), 수수료·정산·실제 입금 금액 / 차이: 처음 발견 실행, 대상·취소 순번, 금액·상태·거래 일시 양쪽, 위험 구분, 처리 기한, 처리로 만든 취소 순번 |
| PG 계약 | 결제사 가맹점(MID, 환경, 키 이름, 웹훅 주소, 정산 주기, 에스크로 확인 번호, 상태), 결제사 가맹점 수수료(수단별 기간 행) |
| 그 밖 | 결제: 결제사 전달 주문명, 부분 취소 가능 여부 / 고객: 결제사 고객 키 |

## 8. 검증 필요 (법·결제사 규칙)

- 결제사 전달 주문번호 재사용, 취소를 승인한 MID로 보내야 하는지, 에스크로용 MID가 따로 필요한지
- 간편결제 안 카드 결제 때 카드 정보가 오는지, 충전금 부분 취소 환원 순서, 충전금 결제가 현금영수증 대상인지
- 가상계좌 입금 알림 검증값, 기한 뒤 입금·다른 금액 입금, 은행 점검 시간
- 인증 후 승인하지 않은 결제의 폐기 시간, 확인 필요 재승인 가능 시간
- 의류 판매가 현금영수증 의무발행업종인지, 자진발급 번호와 기한
- 세금계산서 공급 시기(결제일/출고일), 신청 기한, 수정 사유별 작성 일자, 면세 상품 계산서
- 부가세 원 단위 계산 규칙(토스와 같게), 토스 최소 결제 금액
- 에스크로 적용 범위·수수료·토스 절차, 결제사 고객 키 권장 형식, 결제사 요청 추적ID 형식
- 토스 수수료율·정산 주기, 지운 카드 칸(할부 등)이 5년 보존 대상 "대금결제 기록"에 꼭 들어가야 하는지
