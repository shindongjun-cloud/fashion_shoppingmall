# 고객 2단계 ①: 고객 테이블 설계하는 방법 모두 (처음부터 설계하는 경우)

> 질문(2026-11-24): "우리가 설계한 방식에 국한되어 있는거 같아. 처음부터 진행한다 생각하고 알려줘. 고객 테이블 설계하는 방법 모두 알려줘."

순서는 세 부분입니다.
1. **설계 순서**: 어떤 단계로 진행하는지
2. **결정 지점별 방법**: 단계마다 고를 수 있는 방법과 장단점
3. **쇼핑몰 유형별 조합 예**

---

# 1부. 설계 순서

| 단계 | 할 일 | 예시 질문 |
|---|---|---|
| 1. 요구사항 모으기 | 고객이 하는 일과 운영자가 하는 일을 적습니다. | 가입, 로그인, 주문, 배송지, 등급, 탈퇴, 고객 문의, 마케팅 발송 |
| 2. 고객의 범위 정하기 | "고객"이 누구까지인지 정합니다. | 비회원도? 회사도? 아직 구매 안 한 가입자도? |
| 3. 엔티티 뽑기 | 명사를 모으고 독립적으로 관리할 것을 고릅니다. | 고객, 계정, 주소, 동의, 등급… |
| 4. 식별자 정하기 | 각 엔티티를 무엇으로 구별할지 정합니다. | 번호? 이메일? |
| 5. 관계 정하기 | 관계수(1:1, 1:N, M:N), 선택성, 식별/비식별 | 고객 1명에 주소 몇 개? |
| 6. 속성 정하기 | 기본 / 설계 / 파생 속성으로 나눕니다. | 누적 구매액은 저장할까 계산할까? |
| 7. 정규화 | 반복 값, 부분 종속, 이행 종속을 없앱니다. | 휴대폰1, 휴대폰2 칸 → 연락처 행 |
| 8. 시간 축 정하기 | 상태, 이력, 기간을 어떻게 남길지 정합니다. | 등급이 언제 바뀌었는지 알아야 하나? |
| 9. 보안·법 반영 | 개인정보 암호화, 보관·파기, 동의를 정합니다. | 탈퇴하면 무엇을 지우고 무엇을 남기나? |
| 10. 물리 설계 | 타입, 인덱스, 유니크, 제약조건을 정합니다. | 이메일 중복 가입을 DB가 막나? |
| 11. 검증 | 시나리오로 확인합니다. | 주문 중 탈퇴, 소셜 계정 2개, 비회원이 나중에 가입 |

# 2부. 결정 지점별 방법

## A. 고객의 범위

| 방법 | 내용 | 언제 쓰나 |
|---|---|---|
| 회원만 고객 | 가입한 사람만 저장 | 비회원 구매가 없는 몰 |
| 회원 + 비회원 | 비회원 주문자도 고객으로 저장 | 비회원 구매를 허용하는 몰 |
| 개인 + 조직 | 회사 고객도 포함 | B2B, 단체 주문 |
| 잠재고객 포함 | 뉴스레터 구독자, 이벤트 응모자도 저장 | 마케팅 중심 몰 |

비회원을 고객으로 보지 않는 방법도 있습니다. 이때는 비회원 정보를 주문 테이블에만 두고, 고객 테이블은 회원 전용으로 씁니다.

## B. 고객의 정체 구조

| 방법 | 구조 | 장점 | 단점 |
|---|---|---|---|
| ① 단일 테이블 | 회원 1개에 모든 칸 | 가장 쉽고 빠름 | 칸이 계속 늘고 빈칸이 많음 |
| ② 계정 / 고객 분리 | 로그인 계정 1:1 고객 | 로그인과 쇼핑 데이터가 독립. 탈퇴 후에도 주문 유지 | 연결 규칙이 필요 |
| ③ 1:1 분할 | 회원 + 회원 상세(자주 안 쓰는 칸) | 자주 쓰는 칸만 빠르게 조회 | 조인 증가 |
| ④ 슈퍼/서브타입 | 고객 → 회원 / 비회원 / 사업자 | 유형마다 다른 칸을 깔끔히 분리 | 테이블 수 증가 |
| ⑤ 파티 모델 | 파티(개인·조직) + 역할(고객·거래처·직원) | 한 사람이 여러 역할이어도 한 번만 저장 | 매우 추상적이라 어려움 |
| ⑥ 통합 고객 + 채널 계정 | 통합 고객 1 : N 사이트별 계정 | 패밀리 사이트(여러 브랜드몰) 통합 회원 | 중복 고객 합치기(병합) 규칙 필요 |

**④ 슈퍼/서브타입을 테이블로 바꾸는 3가지**

| 변환 | 내용 | 장단점 |
|---|---|---|
| 하나로 합침 | 한 테이블 + 유형 칸 | 조회 쉬움. 빈칸이 많고 유형별 필수 규칙이 복잡 |
| 서브타입만 | 회원 테이블, 비회원 테이블 | 각각 깔끔. 다른 테이블이 "둘 중 하나"를 가리키기 어려움 |
| 슈퍼 + 서브 | 공통 테이블 + 유형별 테이블 | 다른 테이블은 공통 ID만 가리키면 됨. 조인 필요 |

판단 기준: 유형별로 **칸 자체가 다르면** 나누고, **값만 다르면** 유형 칸 하나로 처리합니다.

## C. 식별자(PK)

| 방법 | 예 | 장점 | 단점 |
|---|---|---|---|
| 자동 증가 번호 | 1, 2, 3 | 작고 빠름 | 외부에 노출하면 회원 수를 추측할 수 있음 |
| UUID | 3f2a…c9 | 추측 불가, 여러 서버에서 생성 가능 | 길고 정렬·인덱스가 느림 |
| 정렬 가능한 랜덤 ID (ULID 등) | 01HX… | 추측 어렵고 시간 순 정렬 가능 | 라이브러리 필요 |
| 업무 코드 | M20261124001 | 사람이 읽기 쉬움 | 규칙이 바뀌면 곤란. 보통 PK가 아닌 UK로 둠 |
| 자연키 | 이메일, 아이디 | 따로 번호가 필요 없음 | 이메일·아이디는 바뀜. PK로는 비추천 |

흔히 쓰는 조합은 내부 PK는 번호, 외부 노출용은 별도 코드나 랜덤 값(UK)입니다.

## D. 로그인(인증) 정보

| 방법 | 내용 | 장단점 |
|---|---|---|
| 회원에 칸 | 아이디, 비밀번호 해시 칸 | 쉬움. 소셜 로그인 추가가 어려움 |
| 소셜별 칸 | kakaoId, naverId 칸 | 수단이 늘 때마다 칸 추가 |
| 로그인 수단 1:N 테이블 | 회원 ─< 로그인 수단(구분, 외부 식별값) | 수단이 늘어도 행만 추가 |
| 비밀번호 별도 테이블 | 비밀번호 해시 + 변경 일시 + 이전 비밀번호 | "최근 3개 재사용 금지", "90일 변경 권고" 가능 |
| 외부 인증 서비스에 위임 | Auth0, Cognito 같은 서비스에 저장하고 우리는 외부 ID만 | 보안 부담이 줄어듦. 외부 의존 |

함께 정할 것: 로그인 시도 기록(잠금 판단), 세션·토큰 저장, 2단계 인증, 본인인증 결과(CI/DI) 저장 여부.

## E. 개인정보 저장 방식

| 방법 | 내용 | 장단점 |
|---|---|---|
| 평문 | 그대로 저장 | 쉬움. 유출 위험 (암호화 의무 범위는 **검증 필요**) |
| 칸 단위 암호화 | 앱에서 암호화해 저장 | 안전. DB에서 검색·정렬 불가 |
| 해시(검색값) | 휴대폰 → 해시값으로 찾기 | 암호화와 함께 써서 검색 가능 |
| 마스킹 값 | 010-****-1234를 따로 저장 | 화면 표시용 |
| 토큰화(보관소) | 개인정보는 별도 보관소에, 고객 테이블엔 토큰만 | 가장 안전. 구조 복잡 |
| 개인정보 분리 테이블 / DB | 개인정보만 따로 모음 | 접근 권한·파기를 한 곳에서 관리 |
| DB 전체 암호화 | 저장 장치 단위 암호화 | 설정만 하면 됨. 앱에서 보이는 값은 평문 |

## F. 이름·연락처 구조

| 주제 | 방법 | 장단점 |
|---|---|---|
| 이름 | 한 칸 / 성 + 이름 분리 | 국내 몰은 한 칸이 흔함. 해외 배송·영문 이름이면 분리 |
| 연락처 | 고객에 칸(휴대폰, 이메일) | 쉬움. 연락처가 여러 개면 곤란 |
| | 연락처 테이블(구분: 휴대폰 / 집 / 회사 / 이메일) | 개수 제한이 없음. 조회 복잡 |
| 국제 | 국가 번호 칸 분리 | 해외 고객이 있을 때 |

## G. 주소

| 방법 | 내용 | 장단점 |
|---|---|---|
| 고객에 주소 칸 1개 | 기본 주소만 | 여러 배송지 불가 |
| 기본 / 추가 주소 칸 | 주소1, 주소2 | 개수가 고정됨(1정규형 위반) |
| 주소록 1:N | 고객 ─< 주소(별칭, 기본 여부) | 개수 자유. 가장 흔함 |
| 주소 마스터 + 고객 주소 M:N | 주소를 한 번만 저장하고 여러 고객이 공유 | 가족·회사 공유 주소. 수정 영향 범위 주의 |
| 주문에 스냅샷 | 주문 때 주소를 복사 | 주소록을 고쳐도 지난 주문은 유지(대부분 함께 씀) |

주소 칸 구조도 정합니다: 한 칸 vs 우편번호 / 기본 주소 / 상세 주소 분리, 도로명·지번 둘 다 둘지, 도서산간 판단용 우편번호.

## H. 상태

| 방법 | 내용 | 장단점 |
|---|---|---|
| 여부 칸 여러 개 | isDormant, isBlocked, isWithdrawn | 모순 가능(휴면이면서 탈퇴) |
| 상태 칸 하나 | 정상 / 휴면 / 정지 / 탈퇴 | 항상 하나라 모순이 없음 |
| 상태 칸 + 변경 이력 | 이력 테이블에 언제·왜 바뀌었는지 | 추적 가능 |
| 상태 기간 테이블 | 상태마다 시작·종료 일시 행 | "3월에 정지 중이었나?" 조회 가능 |
| 상태별 테이블 이동 | 휴면 회원을 별도 테이블로 옮김 | 분리 보관. 옮길 때 실수 위험 (휴면 분리 의무는 **검증 필요**) |

상태 전이 규칙도 정합니다(예: 탈퇴 → 정상 금지).

## I. 등급·고객 분류

| 방법 | 내용 | 장단점 |
|---|---|---|
| 고객에 등급 칸(글자) | grade = "VIP" | 기준·혜택을 모름 |
| 등급 마스터 + FK | 등급 테이블(기준 금액, 혜택) | 기준 변경 쉬움 |
| 등급 이력 | 언제 무슨 등급이었나 | 분쟁 대응, 기간별 혜택 |
| 정책 버전 관리 | 등급 기준 자체의 버전 | 기준이 바뀌어도 과거 산정 설명 가능 |
| 세그먼트 / 태그 M:N | 고객 ─< 고객 태그 >─ 태그 | 등급 외 마케팅 분류 |
| 계산만 | 등급을 저장하지 않고 매번 계산 | 정확함. 느리고 "확정 등급" 개념이 없음 |

## J. 동의

| 방법 | 내용 | 장단점 |
|---|---|---|
| 여부 칸 | isSmsAgreed, isEmailAgreed | 언제·어느 약관 버전인지 모름 |
| 여부 + 일시 칸 | smsAgreedAt | 최근 1회만 남음 |
| 동의 항목 테이블 | 고객 × 동의 항목(현재 상태) | 항목 추가가 쉬움 |
| 약관 버전 + 동의 이력 | 약관(버전) ─< 동의 기록(동의 / 철회) | 동의 증명 가능 (보관 의무는 **검증 필요**) |
| 채널별 수신 동의 | 문자 / 이메일 / 앱 푸시 / 야간 수신을 따로 | 광고 발송 규정 대응 (**검증 필요**) |

## K. 변경 이력

| 방법 | 내용 | 장단점 |
|---|---|---|
| 감사 칸만 | 생성·수정 일시, 생성·수정자 | 마지막 변경만 앎 |
| 주제별 이력 테이블 | 등급 이력, 상태 이력, 아이디 변경 이력 | 목적이 명확. 테이블 증가 |
| 범용 변경 로그 | 테이블명, 칸명, 변경 전 → 후 | 하나로 모든 변경 기록. 조회·해석이 어려움 |
| 스냅샷(SCD Type 2) | 바뀔 때마다 행 전체를 기간과 함께 복사 | 특정 시점 상태 재현 쉬움. 저장량 큼 |
| 이벤트 소싱 | "가입함", "주소 변경함" 같은 사건을 쌓고 현재는 계산 | 완벽한 추적. 매우 복잡 |
| DB 트리거 / CDC | DB가 변경을 자동 기록 | 앱 실수와 무관하게 기록. 설정 필요 |

이력에 개인정보가 들어가면 이력도 파기 대상이 됩니다.

## L. 확장 속성 (체형, 선호 사이즈, 관심 스타일 등)

| 방법 | 내용 | 장단점 |
|---|---|---|
| 칸 추가 | 키, 몸무게, 선호 사이즈 칸 | 쉬움. 항목이 늘 때마다 칸 추가 |
| 1:1 프로필 테이블 | 고객 체형 프로필 분리 | 선택 입력 정보를 분리. 민감도 관리 쉬움 |
| EAV(항목-값 행) | 고객 × 항목 × 값 | 항목 추가 자유. 타입 검사·조회 어려움 |
| JSON 칸 | 한 칸에 묶어 저장 | 유연함. DB 제약·검색이 약함 |

## M. 탈퇴·삭제

| 방법 | 내용 | 장단점 |
|---|---|---|
| 행 삭제(Hard delete) | 바로 지움 | 주문·결제가 가리키는 곳이 사라짐 |
| 소프트 삭제 | 삭제 표시만 | 개인정보가 남음 (파기 의무 **검증 필요**) |
| 익명화 | 행은 남기고 개인정보 칸만 지움 | 주문 유지 + 개인정보 파기 |
| 분리 보관 후 파기 | 법정 보관 정보만 별도 보관, 기간 후 삭제 | 법 대응. 구조 복잡 |
| 유예 기간 | 탈퇴 요청 후 N일 뒤 확정 | 실수 탈퇴 복구 가능 |

함께 정할 것: 진행 중 주문·환불이 있을 때 탈퇴를 막을지, 재가입 제한 기간, 포인트·쿠폰 소멸.

## N. 조직(사업자) 고객

| 방법 | 내용 | 장단점 |
|---|---|---|
| 고객에 사업자 칸 | 사업자번호, 상호 칸 | 직원 여러 명을 담을 수 없음 |
| 사업자 테이블 1:1 | 고객 = 사업자 | 회사 계정 1개를 여러 사람이 공유 |
| 사업자 + 구성원 1:N / M:N | 회사 ─< 소속 회원(역할) | 직원별 로그인·권한 |
| 파티 모델 | B-⑤ | 거래처·고객 겸업까지 처리 |

함께 정할 것: 대표자 여러 명, 사업장 주소 여러 개, 세금계산서 담당자, 사업자 진위 확인.

## O. 고객끼리의 관계

| 관계 | 방법 |
|---|---|
| 추천인 | 고객 → 추천한 고객 (재귀 1:N) |
| 가족 / 그룹 | 그룹 ─< 그룹 구성원 (M:N) |
| 보호자(미성년자) | 회원 → 법정대리인 정보 + 동의 기록 |
| 중복 고객 병합 | 병합 이력(흡수된 고객 → 남은 고객) |

## P. 집계 값 (누적 구매액, 주문 수, 마지막 구매일)

| 방법 | 장단점 |
|---|---|
| 고객에 저장 | 조회가 빠름. 주문 취소·반품 때 맞춰 고치지 않으면 틀림 |
| 매번 계산 | 항상 정확함. 고객이 많으면 느림 |
| 별도 통계 테이블 (배치로 갱신) | 빠르고 원본과 분리됨. 실시간이 아님 |

## Q. 물리 설계에서 정할 것

| 주제 | 예 |
|---|---|
| 유니크 | 이메일·아이디 중복 금지 (탈퇴자 포함할지, 대소문자 구분할지) |
| 인덱스 | 휴대폰 검색값, 가입 일시, 상태 |
| 타입 | 날짜는 시간대 포함, 전화번호는 숫자가 아니라 문자 |
| 제약 | 상태 값 목록, 생년월일 범위, 기본 배송지는 1개만 |
| 기본값 | 상태 = 정상, 가입 일시 = 지금 |

| 유형 | 정체 구조 | 로그인 | 주소 | 상태·이력 | 동의 | 탈퇴 |

## 시작할 때 던질 질문

1. 비회원 구매를 받나요?
2. 회사(사업자) 고객이 있나요? 한 회사에서 여러 명이 쓰나요?
3. 로그인 수단은 몇 가지인가요? 나중에 늘어날 수 있나요?
4. 한 사람이 배송지를 몇 개 쓰나요?
5. 등급·혜택이 있나요? 기준이 바뀔 수 있나요?
6. 탈퇴한 뒤에 무엇을 남겨야 하나요? (주문 기록, 분쟁 기록 — 기간은 **검증 필요**)
7. 브랜드몰이 여러 개거나, 다른 채널과 회원을 통합할 계획이 있나요?
8. 고객 정보로 무엇을 분석하나요? (재구매율, 휴면 위험 등)
