# 6단계: 데이터 무결성 검증 조건 — 공통 + 고객 (2026-11-25)

선생님 9단계 중 6단계 결과입니다. 2026-11-25에 고객·상품 목록 147개(공통 G 16, 고객 C 65, 상품 P 66)를 만들어 사용자와 확인했습니다. **사용자 결정: 147개 모두 유지("나중에 문제되면 그때 빼자")**. 상품(P) 조건은 `../02-product/03-integrity.md`에 있습니다.

## 검사 방법 (최종 방법 칸의 뜻)

| 표시 | 뜻 | 예 |
|---|---|---|
| CHECK | 한 행 안에서 DB가 검사 | 수량 ≥ 0 |
| UK | 중복 금지. **조건부 UK**는 "조건이 맞으면 키 값, 아니면 NULL"을 계산하는 함수 인덱스에 UK를 걸어, 조건이 맞는 행만 중복을 막음(MySQL은 UK에 NULL 여러 개 허용) | 기본 배송지 회원당 1개 |
| FK | 다른 테이블에 있는 값만 허용. **복합 FK**는 칸 두 개를 함께 가리켜 "같은 상품의 컬러인지" 같은 소속까지 검사 | (상품ID, 상품 컬러ID) |
| 권한 | DB 계정 권한. 앱 계정에는 기록 테이블 추가·조회만 허용 | 이력 수정 금지 |
| 트리거 | 여러 행이나 다른 테이블을 보고 DB가 검사 | 가격 기간 겹침 |
| 앱 | 프로그램의 쓰기 함수가 저장 전에 검사 | 판매 관문 |
| 점검 | 매일(그리고 관리자 저장 직후) 도는 점검 작업이 규칙을 어긴 데이터를 찾아 관리자에게 알림 | 판매 중 상품의 가격 공백 |

## DB와 앱 나누기 (2026-11-25 사용자 결정)

예전 구현에서 트리거가 많아 DB가 무겁고 마이그레이션이 까다로웠습니다. 그래서 트리거로 검사하던 조건 77개를 다시 나눴습니다.

**나누는 기준**: DB에 남기는 것은 ① 한 행 CHECK ② UK·FK ③ 돈·법적 증거 ④ 고객·작업·관리자가 여러 곳에서 같이 바꾸는 상태 ⑤ 동시에 두 요청이 오면 앱이 못 막는 것. 나머지(여러 테이블을 읽는 판단, 관리자 화면 한 곳에서만 바뀌는 것, 틀려도 점검으로 찾아 고칠 수 있는 것)는 앱 + 점검.

| 가는 곳 | 개수 | 조건 |
|---|---|---|
| 트리거로 남음 | 9 | C-03, C-04, C-08, C-28, C-48, C-60, P-19, P-63, P-65 |
| 트리거 대신 UK·FK·권한·CHECK (DB에 남음) | 14 | G-16, C-01, C-12, C-13, C-29, C-39, C-47, C-54, P-21, P-30, P-37, P-41, P-47, P-54 |
| 일부는 DB, 일부는 앱 | 3 | C-52, P-38, P-64 |
| 앱 + 점검 | 50 | 나머지 |
| 따로 검사 안 함 | 1 | C-44 (C-04 트리거가 이력을 자동으로 쓰므로 저절로 지켜짐) |

- C-12, C-13은 처음에 앱으로 옮기려 했으나, 개인정보는 덮어쓰기 버그가 나면 점검으로 찾아도 되돌릴 수 없어서 **CHECK + 복합 FK**로 바꿨습니다. 고객 개인정보에 고객 구분 칸을 복사해 넣었습니다(`02-tables.md` 반영). 덤으로 C-01도 DB가 지킵니다.
- 속도: 검사는 저장할 때만 돌고(보기에는 없음), 앱으로 옮긴 조건 대부분은 관리자 작업입니다. 고객 작업에 붙는 검사는 조회 1~2번(수 밀리초)이라 체감 차이가 없습니다. 앱 검사에 쓰는 칸에는 인덱스를 꼭 겁니다(7단계).
- MySQL 8.4는 테이블을 고쳐도 트리거가 지워지지 않습니다(SQLite와 다름). 다만 칸 이름을 바꾸면 트리거 본문도 함께 고쳐야 합니다.

### 앱 + 점검으로 지킬 때 꼭 하는 것 (대책 + 보완)

1. **테이블마다 쓰기 함수 하나**: 예) 판매 시작은 `openSale()`만, 고객 개인정보는 `savePrivacy()`만 씁니다. 가입, 비회원 주문, 정보 수정, 관리자 수정, 파기 작업이 모두 같은 함수를 거칩니다.
2. **지키는지 확인하는 테스트**: 쓰기 함수 밖에서 해당 테이블을 직접 고치는 코드가 있으면 테스트가 실패합니다.
3. **점검**: 매일 + 관리자가 저장한 직후 관련 점검을 바로 돌립니다. 점검이 하루 동안 성공하지 않으면 관리자 알림을 보냅니다.
4. **대량 입력과 seed도 쓰기 함수를 거침**: 엑셀 일괄 등록, 초기 데이터도 같은 함수로 넣고 끝나면 점검을 돌립니다.
5. **자동 테스트**: 각 쓰기 함수가 잘못된 값을 거절하는지 확인합니다.
